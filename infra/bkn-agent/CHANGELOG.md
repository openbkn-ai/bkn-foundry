# Changelog

## [Unreleased]

### Added

- Public executions (start, read, cancel) accept a bkn-safe execution credential (`bex_`), verified at `{BKN_SAFE_BASE}/execution-grants/introspect`. It acts as the person who issued it, for the one knowledge network and Agent it is bound to: a different `context.kn_id` or `agent_id`, or metric design, returns 403 `BknAgent.Execution.Forbidden`. The verified grant id is recorded as the trace's delegation id. Agent settings and the metric designer refuse it (401). Sign-ins and AppKeys are unchanged.

- The graph explorer's `configure_analysis` draws an industry or supply chain (`kind: chain`, one type along a relation from that type to itself in `chainRelByOt`, lanes by `propertyByOt`); a relation that does not link the type to itself is refused. In an analysis, the instructions route industry-chain, supply-chain and upstream/downstream questions to one Cypher query and this chart instead of drawing the chain node batch by node batch.

- Public executions accept an optional `kn_version` (`running`, `draft` or a version number) and `draft_revision` in `context`. Both are sent to Context Loader as `X-Kn-Version` / `X-Kn-Draft-Revision`, pinned into scoped tool calls like `kn_id` (a different model-supplied value returns `ToolScopeMismatch`), and stored with the execution. `draft_revision` without `kn_version=draft` returns 422. Requests without them are stored and run as before, and their scoped tool calls read the running version: a model-supplied `draft`, version number, `draft_revision` or `branch=draft` returns `ToolScopeMismatch` (#1229).

- Add the quality-evaluation assistant to the built-in Agent catalog, preserve administrator changes when seeding it, and carry an explicit Eval purpose through public execution and request deduplication (#2570).

- `DELETE /api/bkn-agent/v1/threads/{thread_id}` deletes a thread's checkpoints and ownership row for its owner (404 for anyone else, 409 while a turn runs); task and execution records are kept.

### Fixed

- A scoped tool call is sent with the run's `context.kn_id` whatever `kn_id` the model wrote, instead of being refused with `ToolScopeMismatch` when they differ. A model that miscopied the network id by one character was refused on every call, and sent the same id again, so the question went unanswered (a scenario regression lost 2 of 8 questions this way). The call still reaches no network but the run's own; a model-supplied version, draft revision or `branch=draft` the run did not ask for is still refused.

- A public execution stream that stays quiet (a model thinking, a slow tool) now sends an SSE comment line (`: ping`) every `BKN_AGENT_SSE_HEARTBEAT_S` seconds, 15 by default. A proxy closed such a stream after its read timeout (60 or 180 seconds), and the closed connection cancelled the run; the graph explorer showed "connection interrupted". Events, their order and sequence numbers are unchanged; a cancel, the run's timeout and a disconnect behave as before (#3272).
- Structured output remembers, per `(base_url, model, thinking mode)` for the life of the process, a provider that refused the native `json_schema` request, and later calls go straight to the prompt fallback instead of paying for the same failed call each time. Only an error that names the `response_format` or `json_schema` counts, with a 4xx or 5xx status other than 408/429 (mf-model-api wraps such a refusal as a 500); a timeout, a rate limit, a bare 502/503, an over-long context or a native result that does not match the schema is not remembered. Models with native support (qwen) are unchanged (#403).
- A structured reply the OpenAI SDK refuses to parse at the output cap (`LengthFinishReasonError`, raised whenever a `response_format` is sent) is treated as truncated: retried once asking for a shorter answer, then failed as `StructuredOutputError … output truncated`; the reasoning tokens are logged, to tell reasoning from answer (a thinking DeepSeek spent all 16384 output tokens on reasoning). Callers that need the answer to fit turn reasoning off for their task with `x-bkn-agent-thinking-mode: disabled`.
- Structured output on providers without the `json_schema` response format (DeepSeek answers 400 "This response_format type is unavailable now"): the prompt fallback now asks for the `json_object` response format, so the reply is valid JSON, and drops it when the provider refuses that too. Raw control characters inside JSON strings are accepted. A reply cut off at the output cap (`finish_reason: length`) is retried with a request for a shorter answer instead of being echoed back, and the final `StructuredOutputError` says `output truncated`, for callers to ask for less per call.
- In an analysis, the graph explorer's `canvas_control clear` no longer tells the model the user will confirm. The instructions said no confirmation follows, the tool said one did, and the model undid and cleared again in a loop.
- BKN project Ontology Assistant limits (`0.2.2/21-ontology-ask-diagnose-limits.sql`): the official limits of `bkn-project-ontology-ask` become `{"max_turns":1,"max_tool_calls":0,"timeout_s":180,"max_output_tokens":16384}` (were 40 s and 1024 output tokens): the diagnose pass needs room for its structured result, which the old cap cut off. Interactive Ask AI stays bounded by bkn-project's 45 s wait. Only the untouched official configuration is changed, recorded as a new current Agent version (changes `["limits"]`) that the Agent row follows; the restore-defaults baseline moves to the official snapshot with the new limits, appended inactive when the configuration was customized. Customized limits, models, tools and history stay. A fresh install starts with the new limits.
- BKN project Ontology Assistant v10 (`0.2.2/20-ontology-ask-diagnose-v10.sql`): a pass `diagnose` for the network diagnosis of the concept modeling page. From the facts bkn-project computes (connected components, references counted over the full table with their polymorphic branches and self references, subtypes, unreachable scenario questions and unmatched requirement concepts) the Assistant judges by five rules (connectivity, reference completeness, participants, reachability, object judgment) and suggests adopting or making relations named by role, choosing identities, adopting or leaving out object types, decision-tracking objects to write back and where unmatched concepts go; it never invents fields or objects and does not rank. One paragraph is added before the Ontology block, in both translations. Only an untouched official v9 is upgraded; customized prompts, history and runtime settings stay. A fresh install starts at v10.
- BKN project ontology guidance (`0.2.2/17-draft-naming-ontology-guidance-v3.sql`, `18-ontology-ask-ontology-guidance-v9.sql`, `19-requirements-ontology-guidance-v14.sql`): draft naming v3, the Ontology Assistant v9 and requirements v14 replace the Naming paragraph by one Ontology block, the same in each, in both translations, after each prompt's lead on where it applies: model the business, not its tables; an object type passes a gate of at least two traits and is named by the singular noun the business uses, a record read from the text of files as the in-text record of its business object; a property is named within its object type; a relation type is named by the role its target plays for its source, read from the source (Part -parent part-> Part), short, unique among the relations of the same source and never by the joining field, the source's name, the cardinality or words such as by or links; metrics, functions, action types, Skills and scenarios each have a name pattern and a definition structure; names and descriptions are in business language. Draft naming names a relation type by that rule instead of the predicate rule. Only untouched official prompts are upgraded; customized prompts, history and runtime settings stay. A fresh install starts at the new versions.
- BKN project naming rules (`0.2.2/14-draft-naming-rules-v2.sql`, `15-ontology-ask-naming-rules-v8.sql`, `16-requirements-naming-rules-v13.sql`): draft naming v2, the Ontology Assistant v8 and requirements v13 add one Naming paragraph, the same in each, in both translations: names say what an item is and descriptions how it is used; an object type passes a gate of at least two traits; records read from files are named as in-text records of their business object; relation types are predicates read from source to target, with no reverse name; metrics, functions, action types, Skills and scenarios each have a name pattern and a definition structure. Draft naming still translates object types, properties and value types faithfully and names a relation type as a predicate. Only untouched official prompts are upgraded; customized prompts, history and runtime settings stay. A fresh install starts at the new versions.
