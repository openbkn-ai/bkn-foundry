# 0.1.4 补丁说明：让第三方 Agent 可直接使用已发布函数

## 结论

本补丁为 OpenBKN `0.1.4` 补齐一条面向第三方 Agent 的标准能力链路：Agent 仅通过
Context Loader MCP 即可发现已发布的函数工具箱、了解函数业务参数、执行函数，并让函数在
沙箱内以当前调用者权限读取业务知识网络。

这不是供应链特例。供应链 sample 只是首个验收场景；平台能力对所有使用
`sandbox_sdk.bkn` 的已发布 Function Toolbox 通用。

**新的 MCP 接口应替换原有绕行方式：**

| 过去的临时做法 | 标准替代方式 | 是否仍是对外推荐路径 |
| --- | --- | --- |
| 用 `run_code` 在沙箱内调用内部函数来发现 Toolbox / Tool | `list_published_toolboxes`、`list_published_tools` | 否 |
| 用本机 CLI 找 Toolbox、列 Tool、执行 Function | `execute_published_tool` | 否 |
| Agent 手工组装 `resolved_context`、快照、Token 或服务地址 | Function 仅接收业务参数；平台透传受管上下文 | 否 |
| Function 调用失败后由 Agent 本地读取 CSV/数据库重新计算 | 函数通过 `sandbox_sdk.bkn` 读取已授权 BKN；失败如实返回 | 否 |

`openbkn` CLI 仍保留给平台管理员和开发者做部署、排障与调试；它不再是第三方 Agent
体验 sample 或调用已发布函数的前置条件。

## 背景

供应链样例需要把物料、BOM、库存、采购和预测等事实保留在业务知识网络中，并由已发布的
原生函数按统一口径完成齐套、交期、替代料和产能计算。客户或生态伙伴应能让自己的 Agent
直接提问，而不需要知道函数服务地址、容器网络、数据库凭据或函数 UUID。

0.1.4 的基础能力已包含 Function Toolbox、Sandbox 和 Context Loader，但这三层之间存在
两个断点：

1. Context Loader MCP 没有公开的“已发布函数目录”和“受管执行函数”接口。Agent 因而改用
   `run_code` 或 CLI 做发现和调用，既不稳定，也让业务操作沾染了平台内部细节。
2. 即使 CLI/Toolbox 成功到达 Function，Function 沙箱内通过 `sandbox_sdk.bkn`
   查询知识网络时也可能收到 `resource_not_disclosed`。直接 MCP 查询成功、函数内部查询
   失败，说明调用身份和受管 Interaction 上下文没有完整传至沙箱，而非样例数据或业务函数
   本身缺失。

## 问题表现与影响

| 表现 | 直接影响 | 对第三方 Agent 的影响 |
| --- | --- | --- |
| `tools/list` 中缺少已发布函数目录能力 | Agent 无法按名称发现函数与参数 | 猜 UUID、依赖 CLI，或错误走 `run_code` |
| 函数调用返回 HTTP 200、但 `exit_code=1` | 业务函数未返回结果 | 常见错误为 `resource_not_disclosed`，难以判断是权限、参数还是数据问题 |
| 函数要求调用方传 `resolved_context` 或快照 | 大量业务数据在调用边界往返 | Agent 需要理解内部载荷，容易超限、过期或伪造 |
| 函数内部 N+1 查询 | 单个 Interaction 可触达操作上限 | 大 BOM 或替代料场景可能超时或达到 128 次操作上限 |
| MCP 宿主的工具目录不一致 | 相同提示在不同 Agent 中表现不同 | 有的 Agent 看见 27 个工具，有的看见旧缓存中的 26 个或其他目录 |

这些问题会把“供应链业务体验”变成“平台接口排障”，不适合作为客户或伙伴 sample。

## 优化方案

### 1. 给第三方 Agent 的稳定 MCP 面

Context Loader MCP 增加三个公开工具：

| 工具 | 作用 | Agent 需要提供的内容 |
| --- | --- | --- |
| `list_published_toolboxes` | 发现当前调用者可见且已发布的函数工具箱 | 可选检索条件 |
| `list_published_tools` | 查看工具箱中启用函数的名称、说明和精简业务参数 schema | Toolbox ID |
| `execute_published_tool` | 在受管 Interaction 中执行一个已发布函数 | Toolbox ID、Tool ID、业务参数、`bkn_context` |

目录接口不返回函数服务地址、内部部署拓扑或不必要的敏感元数据。函数 ID 必须来自本次目录
调用，不要求 Agent 硬编码。

### 2. 用平台可信上下文取代业务载荷透传

Function 的调用 JSON 只保留业务参数，例如：

```json
{"material_code":"606-000989"}
```

受认证请求的授权信息、`conversation_id` 与 `interaction_id` 由服务器捕获并仅在完整时
传入 Function Runtime。业务请求体中的同名伪造字段不会成为可信上下文。若缺失任一字段，
运行时会清空相关沙箱变量，避免池化 Sandbox 复用上一次调用者身份。

Function 再通过 `sandbox_sdk.bkn` 读取调用者被授权访问的知识网络。这样既避免把 BOM、库存
等大明细传给函数，也让权限始终在平台侧校验。

### 3. 将 Function Runtime、Sandbox 与 MCP 作为同一链路交付

相对 GitHub 实际的 `release/0.1.4`，补丁需共同更新三项服务：

| 服务 | 责任 |
| --- | --- |
| `agent-retrieval` | MCP 函数目录、受管函数执行、调用者凭据继承 |
| `agent-operator-integration` | 将服务器捕获的可信授权与 Interaction 上下文转发给 Function Runtime |
| `sandbox-control-plane` | 向函数执行环境注入集群内 Context Loader MCP 地址和受管上下文 |

这三项服务以同一不可变补丁版本发布；不迁移数据库、不修改知识网络，也不把供应链函数代码
打入平台镜像。

### 4. 降低业务函数的查询成本

供应链 sample 的函数同步优化为按问题范围读取：按产品加载 BOM 闭包、按物料集合查询库存和
采购数据、只在题目需要时返回完整明细。以“替代料状态”为例，修复前会对 99 个无关物料逐个
查询库存；修复后只查询替代组成员，库存查询从 99 次降为 2 次。

## 预期的第三方 Agent 使用方式

```text
1. MCP tools/list：确认三个 published-tool 工具可见
2. bkn_start_interaction：创建本题 Interaction
3. list_published_toolboxes：按业务名称发现函数工具箱
4. list_published_tools：找到与问题匹配的具名函数及业务参数
5. Context Loader 查询业务事实（如题目需要）
6. execute_published_tool：只传函数业务参数和本轮 bkn_context
7. 读取结果与 receipt，形成业务回答
8. bkn_finish_interaction：结束本题 Interaction
```

Agent 不需要：CLI、Token、函数 URL、`host.docker.internal`、数据库密码、容器信息、
`resolved_context` 或 snapshot。

## 验证证据与效果

### 平台链路验证

在 localhost 的 0.1.4 补丁环境中，以下链路已实测：

1. 通过主 MCP 发现“供应链原生计算函数”工具箱及其具名函数；
2. 新建受管 Interaction；
3. 调用“标准交期”，函数参数仅为 `material_code=606-000989`；
4. Function 通过 `sandbox_sdk.bkn` 查询 `supply_ontology_hand`；
5. 返回 `exit_code=0`、`leadtime_days=14`；
6. `bkn_finish_interaction` 返回 `execution_status=completed` 且证据状态完整。

相关本机记录见：
[`0.1.4-function-bkn-context-localhost-validation.md`](0.1.4-function-bkn-context-localhost-validation.md)。

### 对第三方 Agent 是否有效

**有效，但需满足两项发布前条件：**

1. 客户环境已安装本补丁，并使用补丁镜像中的三个服务；
2. Agent 所连接的 MCP 宿主已重新建立连接/刷新工具目录，实际能看见三个 published-tool
   工具。

满足后，Agent 可按上述标准链路独立发现和调用函数，不需要将 sample 的内部实现知识写进
提示词。若三个工具缺失、函数内部仍报 `resource_not_disclosed`，应判为环境未就绪，而不是
让 Agent 改用 CLI、本地计算或基础设施探测。

## 发布、验收与回滚

补丁安装包位于
[`deploy/patches/0.1.4-function-bkn-context/`](../../deploy/patches/0.1.4-function-bkn-context/)。

发布顺序：

1. 审核本补丁 PR；
2. 在已审核提交上创建不可变 tag `v0.1.4-supply-sample-p1`；
3. 发布三项服务的多架构镜像，并填写镜像 digest；
4. 客户使用补丁包预览、安装、Kubernetes 就绪检查和 MCP 冒烟验收；
5. 再导入 `bkn-samples` 中的供应链 sample；
6. 最后运行第三方 Agent 的业务体验验证与 BKN-Eval 对比报告。

回滚只恢复这三项服务至安装前记录的镜像 tag，不删除 sample 数据或客户业务数据。

## 主线优化建议

本补丁是 0.1.4 的回补，主线不应直接照搬发布脚本或将供应链 sample 混入平台。主线应将：

- published Function 的目录与执行 MCP 接口，
- 可信身份与 Interaction 上下文的端到端传播，
- Function 在沙箱内读取 BKN 的统一契约，
- MCP 工具目录刷新与一致性验收，

固化为平台公共能力。对外文档应只推荐新 MCP 链路；`run_code` 和 CLI 的旧绕行仅保留在
维护排障文档中，并标记为非 Agent 业务调用路径。
