BKN 知识网络 · 版本管理 API (0.1.0)

Download OpenAPI specification:

Versions of a knowledge network. A network with versioning keeps a draft that all definition writes go to, and numbered versions published from it. Exactly one version is running: reads, queries and the proxy grants of the network use it unless a request names another version with kn_version.

A network without versioning is its main branch, shown as its running version 1: reads of its draft, its running version or version 1 read main, and writes change main. Enabling versioning keeps main as version 1 and starts the draft as a copy of it, so the next publish is version 2.

The branch query parameter, and the branch of a side in a comparison or a stats request, accept default as another name of main; responses still name the branch main.

Operations here enable versioning, publish the draft as a new version, switch the running version (activate), copy a version into the draft or discard the draft's changes (draft/reset), and deprecate, restore and purge versions. The same kn_version / draft_revision read parameters and the If-Match / expected_draft_revision write preconditions apply to the definition APIs of the network; they are described on those operations and in the sections below.

Version statuses

Status Meaning
running The version in use. Only one.
history A published version that is not running; it can be activated, copied or deprecated.
deprecated Hidden from normal use; it can be restored. Professional edition.
purged Its content was deleted. The record stays, reads answer 410.

The Community edition keeps only the running and the previous version: a publish purges the version before the previous one (purged_version in the response), and deprecate, restore and purge are refused with 403 BknBackend.KNVersion.EditionRestricted. full_history in the versioning state tells which edition applies.

Reading a version

Every read endpoint of a versioned network accepts kn_version (running, draft or a version number) and, for the draft, draft_revision. The response carries X-Kn-Version, for the draft X-Kn-Draft-Revision, and X-Kn-Running-Version (the running version, sent whichever version was read). Reading the draft needs modify on the network; reading a version needs view_detail. A version number that was never published is 404 BknBackend.KNVersion.VersionNotFound; a purged one is 410 BknBackend.KNVersion.VersionPurged; a malformed value or a kn_version combined with branch is 400 BknBackend.KNVersion.InvalidVersion. A read that finds its version purged while it ran answers 410 BknBackend.KNVersion.VersionPurged; a read of the draft that was written meanwhile is run once more, and answers 409 BknBackend.KNVersion.DraftRevisionMismatch if the draft changed again. The server holds the response of a versioned read until it has checked this, so a read never returns a mix of two draft revisions. On an unversioned network kn_version accepts only running, which means main (any other value is 400 BknBackend.KNVersion.NotVersioned), so callers can use one code path for both.

A network created with versioning (see versioning of the create request) has no running version until its first publish: reads of the running version return an empty network, and X-Kn-Version and X-Kn-Running-Version are not sent.

Concept search (search over concepts) reads the concept index of the version it resolves to. Every published version has an index of its own, written in the same transaction that publishes it; the draft's index is updated by every write to the draft, so a search over kn_version=draft always sees the latest edit. Purging a version, or turning versioning off, deletes its index. Two kinds of endpoint do not read the definitions of a chosen version: the validation endpoints check the request body (the version only matters for the existence check of the network), and overview-graph reads the branch named by branch (main, which holds the running version, by default).

Writing to the draft

A write to a versioned network always goes to the draft and each write adds one to the draft revision, returned as X-Kn-Draft-Revision. What a write must send to detect concurrent changes depends on the operation, and is checked only on versioned networks (an unversioned network accepts the same headers and parameters but never requires them):

Write Precondition
Create definitions (POST) none
Update one definition (PUT, PATCH) If-Match with the definition's revision (also its ETag)
Delete definitions (DELETE) If-Match for one definition, or expected_draft_revision
Import an archive, replace the draft, change skill_content of the network expected_draft_revision

A write without its precondition is 428 BknBackend.KNVersion.PreconditionRequired; a stale If-Match is 409 BknBackend.KNVersion.DefinitionModified with current_etag in the error details; a stale expected_draft_revision is 409 BknBackend.KNVersion.DraftRevisionMismatch. A write that names kn_version, or a branch other than main or draft, is refused with 400 BknBackend.KNVersion.InvalidVersion; main is accepted and means the draft.

The same rules cover the object-metric endpoints (bkn-object-metrics-v1.yaml, Enterprise edition): their writes go to the draft, an update needs If-Match, and a delete needs If-Match or expected_draft_revision.

Metrics

In the Enterprise edition a publish also publishes the metrics of the draft. A metric whose latest version is validated is published with the network when every metric it depends on is already published or is published in the same batch. The other metrics are left as they are and reported in warnings of the publish response: unvalidated_metric for a version that is still a draft or no longer passes validation, and metric_dependency_unmet for a validated version whose dependency is not published. The versions the publish made live are listed in published_metrics. An edition that does not serve metrics publishes none and reports no metric warnings. Metric version numbers are allocated per network, not per branch, so a number names one version in every branch.

Idempotency

Operations that change versions accept an Idempotency-Key header (at most 64 characters). Retrying with the same key returns the first call's result and status without running it again.

Permissions

Enabling versioning, publishing, activating, resetting the draft, building the draft index, deprecating and restoring need modify on the knowledge network; purging needs delete; reading the state, versions, events and referenced resources needs view_detail. See ../knowledge-network-authorization.md.

All APIs are exposed under /api/bkn-backend/v1 and require OAuth2 authentication.

Publish the draft as a new version

Publishes the draft as the next version and makes it the running version, in one transaction that also switches the network's main branch, the version's concept index and proxy grants to it. The request must name the running version and the draft revision it was prepared against, so a publish never goes out over a change the caller did not see.

Refused with 400 BknBackend.KNVersion.ValidationFailed when the draft references things that do not exist: the ends of a relation type, the object type of an action type, the members of a concept group, the action types of active schedules (read from main), and bound functions, Skills or knowledge bases that are gone. Its details list problems. The check does not cover metric references, permissions on referenced knowledge bases or the proxy. Refused with 409 BknBackend.KNVersion.NothingToPublish when the draft has no unpublished changes (the first version of a network without a running version publishes even without edits), and with 409 BknBackend.KNVersion.DraftBaseOutdated when the running version was switched after the draft took its base, unless allow_outdated_base is true. In the Community edition the publish purges the version before the previous one.

The concept index of the new version is written inside the publish; if that fails the publish is rolled back and answers 503 BknBackend.KNVersion.ConceptIndexFailed, and can be retried. Metrics are published with the network as described under Metrics; the response lists them in published_metrics and what it left out in warnings. A retry with the same Idempotency-Key returns the version record only, without warnings and published_metrics.

Copy a version into the draft, or discard the draft's changes

Replaces the whole draft with a version. With from_version the draft becomes a copy of that version (a copy event); without it the draft returns to the running version, discarding its changes (a discard event). expected_draft_revision is required. When the draft has unpublished changes the request is refused with 409 BknBackend.KNVersion.DraftHasChanges (details draft) unless overwrite_changes is true.

header Parameters
Idempotency-Key
string <= 64 characters

Makes a version operation safe to retry, at most 64 characters. Retrying with the same key returns the result and status of the first call without running the operation again; a key already used for a different operation or target version is 422 BknBackend.KNVersion.IdempotencyKeyReused.

Request Body schema: application/json
required
from_version
integer >= 1

The version to copy into the draft. Left out, the draft returns to the running version.

expected_draft_revision
required
integer <int64>

The draft revision the caller saw. A different current value is 409 DraftRevisionMismatch.

overwrite_changes
boolean
Default: false

Confirms overwriting unpublished changes of the draft (DraftHasChanges otherwise).

Make the concept index of the draft current

Ensures the concept index of the draft matches its current revision, so that concept search over kn_version=draft finds the latest edits. The draft's index is kept current on every write, so the build is reported ready for the current revision; 202 is reserved for a build that runs in the background.
