Download OpenAPI specification:

A capability binding records that a Skill or a ToolBox tool belongs to a knowledge network. The master data stays in the execution factory; the binding holds only the reference, so creating, publishing and indexing capabilities is unchanged by these endpoints.

Identity

A capability is identified by three parts:

capability_type box_id capability_id
skill empty skill_id
function box_id tool_id
knowledge_base empty knowledge base id

box_id is required for a function because a tool id is scoped to its box in the execution factory, and it is the same name the execution factory, Context Loader and Studio already use. A skill has no container and omits it, and so does a knowledge base.

A knowledge_base is an Enterprise knowledge base served by kb-api. Mounting one checks with kb-api that it exists (400 KnowledgeBaseNotSupported where kb-api is not deployed) and that the editor holds query_data on it. Publishing then lets the network's managed proxy read the whole knowledge base through kb-api's read API. Like a Skill, the grant is best effort: if the editor later loses access, only that knowledge base becomes unreadable through the proxy.

The stored column behind it is type-neutral (f_owner_id) so a later capability type can bring a different kind of container without a migration; that name does not appear on the wire. A box_id sent with a skill is dropped rather than stored — keeping it would create a second row for the same skill that the unique key cannot collapse, and repeated mounts would stop being idempotent.

What a binding answers

A binding answers "which capabilities does this knowledge network have", not "which capability is relevant to this question". Listing does not replace retrieval: a network with dozens of Skills and tools needs the execution factory's search endpoints.

The public list includes model-referenced tools by default, including tools with no stored binding. Set mounted_only=true for mount-management views: it returns only stored bindings, pages them directly in the database, and does not scan object or action types. The default remains unchanged for callers inspecting model dependencies.

Scope and branch

Bindings are per branch. Creating a branch copies them, deleting a branch clears them, and the count in the knowledge-network statistics follows the branch being viewed.

Idempotency

Mounting is a statement about membership, not an event. Mounting a capability that is already bound returns the existing binding rather than failing, and repeating an entry inside one request produces one row.

Mounting validates the target

A mount checks the capability against the execution factory before writing anything, and the two failures it can report are deliberately distinct: the target does not exist (check the id) and the target exists but is not usable (publish the tool box or skill, or enable the tool). Collapsing them into one error would leave the caller guessing which fix applies.

Validation runs over the whole request first. A batch whose fourth capability is unknown writes nothing at all rather than leaving three bindings behind.

When the execution factory is unreachable the answer is 502 and no write. A binding recorded without validation cannot be told apart later from one that was checked.

Two things are deliberately not checked. metadata_type is ignored, so openapi and function tools are equally bindable — a binding names a tool, and the box is only the execution factory's container for it. And mounting does not require permission to execute the target: binding is a modeling action by the network's owner. At call time the caller needs the network's execute permission; the managed proxy and execution factory then validate the exact binding, target lifecycle and delegated grant without requiring direct target permission.

Whole-box mounting

{"capability_type": "function", "box_id": "box-x", "all_tools": true} mounts every enabled tool of that box. The expansion happens at write time: the stored rows are ordinary tool-level bindings carrying bound_as_box: true, so the read path never expands anything and any single row can be released on its own.

Tools added to the box afterwards are not inherited. That is the point of expanding rather than storing a box-level scope: on a shared box, inheritance would let someone else's edit widen this network's reach. The list view reports how many tools of a box are not mounted so they can be added deliberately.

Disabled tools are skipped, on the same terms that reject them when named directly. A box with no tool to mount is a 400, not a silent success — "I mounted the box" and "nothing happened" must not look alike.

Metadata is backfilled, not stored

A binding stores only the reference. Names, descriptions and statuses are read from the execution factory when the list is served, so they never go stale and the master data stays in one place.

The reads are shaped around what costs what. Function metadata comes per tool box, not per tool: the box endpoint inlines its tools, so a page of twenty function bindings across three boxes costs three calls. Skill names are one call for the whole page. Only a skill's description and status must be read one skill at a time, which is why they are behind with_detail=true rather than always paid.

Dangling bindings are marked, never deleted

A binding whose target has been removed from the execution factory comes back with status: "missing". It is not deleted: removing it silently would erase the evidence that the network once pointed at something, and it is the owner's decision whether to clean it up or restore the capability. When a whole tool box is gone, every binding under it is marked and the box appears in boxes with box_missing: true.

This matters because retrieval treats a dangling reference as simply absent — it matches nothing and says nothing. Without the marker the only symptom is "the navigation says four functions but only three ever come back".

Whole-box top-up

A whole-box mount is expanded at write time and does not follow the box afterwards, so tools added later are not bound. boxes reports total_tools, mounted_tools and unmounted_tools per box so the list can show "20 of 23 mounted" and offer to add the rest deliberately. Disabled tools are excluded from the totals: they are not something a top-up would add.

These counts are per branch, not per page. Pagination slices the entry list, not the box, so counting a page against a box-wide total would read "10 of 23 mounted" for a box that is fully mounted and offer a top-up that does nothing. When the count cannot be established the box is omitted from boxes and metadata_available turns false, rather than published with a number that would send the caller after tools that are already bound.

When a metadata service is unavailable

Listing degrades rather than fails: the bindings come back in full with empty metadata and metadata_available: false. Listing memberships is the point of the endpoint and the names are decoration — failing the request would take the mount UI down with the factory. The flag exists so an empty name is not read as a deleted capability; an outage and a deletion must not look alike. For knowledge bases, this also covers an unset KB_API_URL: without a configured kb-api the backend cannot establish whether the target exists. Only a confirmed not-found response marks a knowledge base missing. Export fails with metadata unavailable until the configuration or service recovers, rather than silently dropping these mounts.

Navigation-only knowledge networks

A caller who cannot view the knowledge-network detail but can view at least one child resource may open the network as a navigation-only shell. For that caller, the public list returns a canonical empty result (entries: [], total_count: 0, boxes: []) for every supported capability filter. Capability bindings belong to the network detail and have no child-level authorization resource, so the service does not read binding rows, model provenance, or execution-factory metadata in this mode. This avoids both a misleading permission error in the shell and disclosure of capabilities the caller cannot view.

Both metadata_available and sources_available are true in this canonical empty result: there are no returned rows or sources left unresolved, so the result is complete. These flags do not imply that the execution-factory or model-provenance dependencies were called.

A caller with neither knowledge-network detail access nor any visible child still receives 403. Authentication and permission-service failures also remain errors; they are never converted to an empty list.

The internal face answers differently

GET /api/bkn-backend/in/v1/knowledge-networks/{kn_id}/capabilities returns bare references — binding id, capability_type, box_id, capability_id — with no metadata, no paging and no box summaries.

Context Loader calls it on every recall to learn what is in scope before asking the execution factory to search inside that scope. Backfilling names here would add a service hop per recall to produce exactly what the caller is about to fetch itself, and paging it would hand back a subset of the scope, which is a different scope. A network with no bindings resolves to an empty list rather than an error: "this network has no skills" is an answer, not a broken dependency. The internal endpoint accepts either network view_detail (discovery) or network execute (execution scope resolution); public discovery and execution endpoints each enforce their own operation before calling it.

Public paths use /api/bkn-backend/v1; the internal face uses /api/bkn-backend/in/v1.

box_id
string

Filter by owning tool box. Only meaningful for functions.

owner_id
string

Accepted spelling of box_id, kept for callers that name the tool box that way. A non-empty owner_id wins when both are sent; new callers should send box_id.

metadata_type
string
Enum: "openapi" "function"

Narrow function bindings to one kind of tool box: openapi or function. The value belongs to the box rather than the binding, so it is resolved to the set of boxes of that kind and applied as a query condition — paging and total_count are therefore over rows that already match. A box whose kind cannot be read counts as function, which keeps a dangling binding visible in one of the two lists rather than neither. The kind belongs to a tool box, so this implies type=function: skills and MCP tools are never returned alongside it. Any value other than the two is a 400.

with_detail
boolean
Default: false

Also fill description and status. A skill's detail is read one skill at a time, so this is opt-in; function detail arrives with the box response either way.

mounted_only
boolean
Default: false

Return stored capability bindings only. Excludes tools referenced solely by object or action types; total_count and pagination cover stored bindings. This mode skips model provenance reads, so sources contains only the direct mount kind and sources_available is false. Defaults to false to preserve the existing dependency inspection response.

offset
integer

Offset. Defaults to 0.

limit
integer

Page size. Defaults to 10.

sort
string
Enum: "create_time" "update_time"

Sort field. Defaults to create_time.

direction
string
Enum: "asc" "desc"

Sort direction, asc or desc. Defaults to desc.

kn_version
string
Example: kn_version=draft

Which version of a versioned knowledge network to read: running (the default), draft, or a version number. Reading the draft needs modify on the network; reading any other version needs view_detail. Do not combine it with branch (400 BknBackend.KNVersion.InvalidVersion, which is also the answer to a value that is not running, draft or a positive integer). A version that does not exist is 404 BknBackend.KNVersion.VersionNotFound and a purged one is 410 BknBackend.KNVersion.VersionPurged. A network without versioning is shown as its running version 1: running, draft and 1 are accepted and all mean the main branch; any other value is 400 BknBackend.KNVersion.NotVersioned.

Not accepted on writes: a write to a versioned network always goes to its draft, and a write that names kn_version is refused with 400 BknBackend.KNVersion.InvalidVersion.

A write to a versioned network that sends branch=draft only changes the draft, which is published later. A write without branch, or with branch=main, is a direct write: it goes to the draft and is published as a new version in the same request, so later reads of the running version see it, as on a network without versioning. A direct write needs no If-Match or expected_draft_revision (they are still checked when sent), and its response carries the new version in X-Kn-Version. A direct write is refused with 409 BknBackend.KNVersion.DraftHasChanges while the draft holds unpublished changes, which it would otherwise publish too; an import with overwrite_changes=true replaces them instead. Two direct writes to one network at the same time can meet this way: the second sees the first one's write in the draft before it is published, and can be retried. A draft left on another version by a switch of the running version, with no changes of its own, is first put back on the running version. When the write or its publish fails, the draft is put back as it was before the write and the publish error is returned, for example 400 BknBackend.KNVersion.ValidationFailed.

A network without versioning is its main branch, shown as v1: writes without branch change main, as they always did, and branch names a branch as it is. Enabling versioning (see the versions API) is what makes main its running version 1 and starts the draft.

draft_revision
integer <int64> >= 0

With kn_version=draft, the draft revision the caller expects to read (see the revision of draft in the versioning state, and the X-Kn-Draft-Revision response header). A different current revision is refused with 409 BknBackend.KNVersion.DraftRevisionMismatch.

Release capability bindings

Releases by binding ID, comma separated for a batch. IDs that are already gone are not an error. Binding IDs are used rather than the capability identity because a tool-level binding needs box_id as well to be located, and identifiers containing special characters would have to be escaped in the path.

path Parameters
kn_id
required
string

Business knowledge network ID

binding_ids
required
string

Comma-separated binding IDs

query Parameters
branch
string

Branch. Defaults to main.

expected_draft_revision
integer <int64> >= 0

The draft revision the write is based on. On a versioned network it is required when the request changes the draft as a whole (an import, or skill_content of the network) and accepted instead of If-Match when a delete removes several definitions at once. A different current revision is refused with 409 BknBackend.KNVersion.DraftRevisionMismatch. Accepted but never required on a network without versioning, or by a direct write (see kn_version).

header Parameters
If-Match
string

The revision of the definition being changed or deleted, as returned in its revision field or ETag response header (quotes are optional). Required on a versioned network for an update (PUT, PATCH) and, for a delete of one definition, unless expected_draft_revision is sent; missing it is 428 BknBackend.KNVersion.PreconditionRequired. A stale value is 409 BknBackend.KNVersion.DefinitionModified, whose details carry current_etag. If-Match names one definition: with several ids in the path send expected_draft_revision instead. Accepted but never required on a network without versioning, or by a direct write (see kn_version).

Resolve the capability references bound to a knowledge network

Internal face. Returns bare references — no execution-factory metadata, no paging and no box summaries — so the response schema is CapabilityReferenceList, not the public CapabilityBindingList. See "The internal face answers differently" above for why.

The caller is identified by the internal account headers rather than a token. It is accepted with either network view_detail (discovery) or network execute (execution scope resolution); the public discovery and execution endpoints each enforce their own operation before calling it.
