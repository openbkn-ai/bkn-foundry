BKN Capabilities (0.1.0)

Download OpenAPI specification:

A capability binding records that a Skill or a ToolBox tool belongs to a knowledge network. The master data stays in the execution factory; the binding holds only the reference, so creating, publishing and indexing capabilities is unchanged by these endpoints.

Identity

A capability is identified by three parts:

capability_type owner_id capability_id
skill empty skill_id
function box_id tool_id

owner_id is required for a function because a tool id is scoped to its box in the execution factory. A skill has no owning container, so an owner_id sent with a skill is dropped rather than stored — keeping it would create a second row for the same skill that the unique key cannot collapse, and repeated mounts would stop being idempotent.

What a binding answers

A binding answers "which capabilities does this knowledge network have", not "which capability is relevant to this question". Listing does not replace retrieval: a network with dozens of Skills and tools needs the execution factory's search endpoints.

Scope and branch

Bindings are per branch. Creating a branch copies them, deleting a branch clears them, and the count in the knowledge-network statistics follows the branch being viewed.

Idempotency

Mounting is a statement about membership, not an event. Mounting a capability that is already bound returns the existing binding rather than failing, and repeating an entry inside one request produces one row.

Not covered here

Whole-box mounting, the write-time check that the target exists and is published, metadata backfill and dangling marking arrive with the rest of the capability binding work; this file describes the CRUD surface only.

Prefix aliases: every path below is also served under /api/ontology-manager/v1, and the internal face under /api/bkn-backend/in/v1 and /api/ontology-manager/in/v1.

Release capability bindings

Releases by binding ID, comma separated for a batch. IDs that are already gone are not an error. Binding IDs are used rather than the capability identity because a tool-level binding needs owner_id as well to be located, and identifiers containing special characters would have to be escaped in the path.

path Parameters
kn_id
required
string

Business knowledge network ID

binding_ids
required
string

Comma-separated binding IDs

query Parameters
branch
string

Branch. Defaults to main.

Responses

/api/bkn-backend/v1/knowledge-networks/{kn_id}/capabilities/{binding_ids}
