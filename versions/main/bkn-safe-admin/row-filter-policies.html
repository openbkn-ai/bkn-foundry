BKN Safe Enterprise Row-filter Policy Management API (1.0.0)

Download OpenAPI specification:

Manages one fixed-condition object-instance row-filter policy for a user or role on one published object type. Row filtering is evaluated only after the caller has the object's base query_data permission and can therefore narrow, but never grant or expand, query access.

This first version supports only administrator-entered fixed values. It has no user/department auto-matching, identity-field mapping, SQL, scripts, regular expressions, nested Boolean groups, or legacy policy migration.

The API is available only when the Enterprise row-filter capability is assembled and licensed. Reads and writes require either the matching platform user- or role-administration permission, or authorize on the resource's authorization-management root. For a knowledge-network child, that root is its knowledge network; the caller must also be able to view the concrete object type. A resource authorizer may configure policies for users or custom roles only within that boundary; this does not grant role membership access or authority over another knowledge network. Creating or replacing a policy requires an enabled user or custom role; deletion remains available for stale subjects. Updates use optimistic locking; clients must read the current revision, submit it as expected_revision, and handle 409 revision_conflict without automatically overwriting the newer policy.

Create, replace, or delete one explicit row-filter policy

The request atomically updates the policy and its audit record. For a create, expected_revision must be null. For an update or deletion it must equal the revision returned by the latest GET. policy: null deletes an existing policy and is an idempotent no-op when none exists. A deleted policy no longer participates in user/role policy composition; deletion does not mean “deny every row”.

Explain the row-filter rules currently applicable to a subject

For a user, returns the direct policy and normalized effective predicate. Matching role policies are included only for callers holding platform admin-role:view; resource-root authorizers receive the same effective predicate without role-membership sources. Complete user/role policies are ORed; conditions inside each policy retain that policy's AND or OR relation. For a role, role_policy_only is true and no user-effective predicate is calculated because a role alone does not identify a concrete user's full role membership. The response never includes filtered object instances.
