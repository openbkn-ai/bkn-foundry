Context Loader knowledge network tools.

Suggested exploration order:
1. Call list_knowledge_networks first to obtain a kn_id. Most other tools require kn_id.
2. Call search_schema with natural language to discover object types, relation types, action types, metric types, data_source.id, supported condition operations, and physical columns.
3. Pick the query tool based on the task.

Query routing:
- Use query_object_instance for single object-type filtering, sorting, and cursor-style pagination.
- Use run_sql for joins, aggregation, ranking, GROUP BY, COUNT, SUM, AVG, and cross-table analysis. Use read-only MySQL SQL. Reference tables with placeholders such as {{.resource_id}} where resource_id comes from search_schema or list_resources. Use physical column names from search_schema with include_columns=true or from describe_resource.
- Quote MySQL identifiers with backticks when needed (for example, `order_id`); double quotes are string literals, not identifiers.
- Use query_instance_subgraph when you can already name the path - which object types it passes through and which relation types connect them - to pull instances along that template, with per-node filters and sorting.
- Use explore_subgraph when the topology is unknown and the question is what something connects to. Give a source object type, a direction and a hop count; the engine finds the paths. Do NOT enumerate relation types to hand-assemble a path for query_instance_subgraph instead - that turns discovery into a combinatorial search.
- Use get_action_info to discover actions that can be executed for object instances.

Metrics, object type first. Never re-derive a modelled metric in run_sql — its formula lives in the metric definition:
1. Recall the object type with search_schema or get_kn_detail. In the get_kn_detail summary, only object types with related_metric_count > 0 have metrics.
2. Call get_object_types(ids) to see what that object type offers: logic_properties with data_source.type=metric are the instance-level ones; related_metrics lists every metric scoped to the object type, including those not bound to any logic property.
3. Compute the one you picked:
   - instance level, bound to a logic property: get_logic_properties_values
   - class level, or not bound to a logic property: query_metric with the metric_id, plus optional condition / analysis_dimensions / time
   - only when nothing is modelled as a metric: run_sql

Direct data-layer path:
- Use list_resources to list data resources with resource_id, name, type, and catalog_id. To answer "which tables does this knowledge network have", pass kn_id: it returns every resource bound to that network at once, and reports object types with no binding under unbound and unreachable bindings under missing. Without kn_id it pages the account-wide resource pool and can be filtered by catalog_id / type. Never fetch one page without kn_id and intersect it yourself — a large pool guarantees misses.
- Use describe_resource to inspect a resource's physical columns and connector type.
- Then use run_sql with table placeholders and physical column names.

Tips:
- For aggregation questions such as "total Y by each X" or ranking tasks, go directly to run_sql instead of approximating with query_object_instance sorting.
- Never copy the literal placeholder name "resource_id"; replace it with the actual id returned by search_schema or list_resources.
