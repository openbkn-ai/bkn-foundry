ContextLoader 知识网络查询工具集使用指南。

受管交互流程：

处理每个新的用户问题时：

1. 调用 bkn_start_interaction，传入完整问题、当前 Agent 名称和 conversation_mode。
   当前聊天中的首个受管问题使用 conversation_mode=new，不传 conversation_id；
   后续问题使用 conversation_mode=continue，并传入上一次返回的 conversation_id。

2. 本工具返回 conversation_id 和 interaction_id。
   conversation_id 在整个对话过程中保持不变；
   interaction_id 在当前用户问题开始后、回复完成前保持不变。
   本轮调用其他工具时传入 bkn_context: { conversation_id, interaction_id }。

3. 回复用户前，调用 bkn_finish_interaction。
   正常完成传入 outcome=completed 和最终答案；
   未完成时传入 failed、cancelled 或 handed_off，并可附原因。
   然后回复用户。

下一个用户问题会开始新的 Interaction，并继续使用当前 conversation_id。

探索顺序：
1. list_knowledge_networks 获取 kn_id（其余工具都需要 kn_id）。
2. get_kn_detail（默认 detail_level=summary，体积小）先看概念组清单。每个分组带 name/tags/comment，据此选出 1-3 个与问题相关的分组。
3. search_schema 在选中分组内找对象类：传 search_scope={"concept_groups":[选中的分组 ID]}，返回 ot_id、属性、索引能力（共用的算子放在对象类的 index_operations，支持它的属性写 indexed=true）、data_source.id。
   默认精简（schema_brief=true，省约 70%，够写查询）；要属性备注/主键/标签的完整 Schema 才传 schema_brief=false。
   回退：概念组清单为空、凭语义判断不出该选哪个、或问题跨越三个以上分组时，不传 concept_groups 直接全网检索。
   不传分组不会报错，只是召回范围是整网，返回更大也更杂——能选就选。
4. 要某对象完整字段映射再 get_object_types(ids)，要关系 mapping_rules 再 get_relation_types(ids)。别一上来就 detail_level=full。
5. 按查询类型选工具（见下）。

网络说明与业务计算：get_kn_detail 顶层的 comment 是网络作者写的说明；写了问答路由、指标或时间基线时，优先按它选择函数、技能和指标，并照它的口径作答。可售、齐套缺料、产能、交期、替代料、BOM 展开这类业务计算，网络挂载了函数时用 search_capabilities 找已发布函数、execute_tool 执行，以函数结果为准；不要用原始数据、Cypher 或 SQL 自行推算这些口径。

查询分流：
- 单对象类过滤 + 排序 + 分页（field op value，可 and/or 组合）→ query_object_instance；比较算子（==/!=/in/>/range/like/regex 等）按属性 type 自行判断，索引算子 match / knn 才看索引能力：search_schema / search_instance 把共用的算子放在对象类的 index_operations，支持它的属性写 indexed=true，能力不同的属性自带 condition_operations（get_object_types 始终逐属性给全量）——两个键都没有才说明字段没建索引，而没建索引不代表不能过滤；text 字段走本地索引时，==/!=/in/not_in 使用 keyword。新保存或重新保存的配置会自动补齐；若旧配置/旧索引返回 400 缺 keyword，重新保存资源配置后新建构建任务，或改用 match。默认 keyword 只索引长度不超过 256 的值，超长值不能精确比较。like/not_like 是字面子串包含（不要自己拼 %），要通配用 regex（锚定与大小写敏感性随资源存储而变，「包含」写 .*词.*）。
- 聚合 / 统计 / 排名（SUM、COUNT、AVG、GROUP BY、按聚合值排序、跨表 join）→ run_cypher（见下：count/sum/avg/min/max，按 RETURN 中其余列自动分组，配 ORDER BY / LIMIT），它只需要知识网络授权。口径已经建成指标的走 query_metric 或 get_logic_properties_values；网络挂了函数的按函数口径走 execute_tool。query_object_instance 不支持聚合。
- 已知路径长什么样（说得出经过哪几个对象类、走哪几条关系类）→ query_instance_subgraph，按路径模板批量取数，可逐节点加过滤与排序。
- 跨对象类的多跳查询、路径上带过滤、或要在路径结果上聚合 → run_cypher（只读 Cypher）。标签写对象类 id 或名称，关系写关系类 id 或名称，属性写逻辑属性名——都用 search_schema / get_object_types / get_relation_types 返回的名字，不需要 resource_id，也不需要物理列名，关系怎么 join 由服务端按关系类定义补。支持多个 MATCH、逗号分隔的多条路径、WHERE（= <> < > <= >=、IN、IS NULL、AND/OR/NOT、$参数）、RETURN（AS 别名、DISTINCT、count/sum/avg/min/max，聚合按 RETURN 中其余列自动分组）、ORDER BY / SKIP / LIMIT。不支持 OPTIONAL MATCH、WITH、UNION、变长路径 [:R*1..3]、函数与算术、返回整个节点；一条查询最多 8 条关系、9 个节点。被拒时报错会指名是哪个语法，按提示改写；子集表达不了的口径改走已建模指标或已发布函数。
- 不知道拓扑、要发现关联（「这张订单牵连到什么」「这个供应商两跳内碰到谁」）→ explore_subgraph，只给起点对象类 + 方向 + 跳数，路径由引擎散。**别为了用 query_instance_subgraph 去先枚举关系类拼路径**，那是把探索硬凑成取数，路径一长就组合爆炸。
- 反向上溯 / 反查用途（「这个零件被哪些成品用到」「这条记录往上挂在谁身上」）→ 同样是 explore_subgraph，传 direction=backward 沿入边走。**别在 run_code 里逐节点循环调 query_object_instance 自己爬父链**：那会把一次交互的操作预算耗光，中途被拒。
  注意 path_length 上限是 3。层级更深（多级 BOM 之类）走这条到不了根，改用已发布函数，或一次性分页取回全表在本地遍历——run_cypher 不支持变长路径，递归展开写不出来。
- 对象可执行行动召回 → get_action_info。

指标取数（OT 优先，三选一，禁止自行重写已建模指标的口径）：
1. 先锁定对象类：search_schema 或 get_kn_detail（summary 里 related_metric_count>0 的对象类才有指标）。
2. get_object_types(ids) 看该对象类下有什么：logic_properties（data_source.type=metric）是实例级，related_metrics 是这个对象类 scope 下的全部指标（含未绑逻辑属性的）。
3. 选定后计算：
   - 实例级 + 已绑逻辑属性 → get_logic_properties_values
   - 类级 / 未绑逻辑属性 → query_metric（传 metric_id，可选 condition / analysis_dimensions / time）
   - 指标压根没建模，才用 run_cypher 按对象类与关系类现算

提示：聚合类问题（如「每个 X 的 Y 总数/排名」）用 run_cypher 在模型上写（如 MATCH (x:X)-[:R]->(y:Y) RETURN x.name AS name, sum(y.v) AS total ORDER BY total DESC LIMIT 10）；不要用 query_object_instance 的 sort 近似。

成员资格、多条件阈值、求和、计数和去重也必须下推到 run_cypher 或已建模指标。用户同时要求总数和明细时，让同一次可重算查询返回聚合结果及对应明细，或用共享条件的两次查询分别返回。不能先用 query_object_instance 拉回多页数据，再在 Agent 上下文里自行筛选、计数或去重；这种上下文计算无法形成完整、可重放的业务证据。
