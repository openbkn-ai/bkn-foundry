# BKN Project

[中文](README.zh.md) | English

`bkn-project` builds and publishes knowledge networks from projects. Each
release is imported into bkn-backend as a new knowledge network
(`<base_id>_<version>`) instead of overwriting the live one, and the release
history is kept as a lineage. See issue #2520 and epic #2519.

## Current Capability Scope

- Release store (`t_bkn_project_release`).
- Git lineages: one bare repository per lineage under `/data/git` (a
  persistent volume in the Helm chart). `main` mirrors the network's running
  version; projects work on their own branches and sync `main` into them with a
  semantic three-way merge.
- Drift check between the network's draft and `main`.
- Publishing through the network's versions (bkn-backend versioning,
  bkn-foundry#1229): a project's network keeps versions and its id. A release is
  first prepared: the project branch replaces the network's draft, where the
  project's scenario questions are answered (`kn_version=draft`); the running
  version does not change. Publishing it then makes the draft the running
  version for every consumer at once, labelled `v<version>`, and tags
  `v<version>` in git. Consumers keep their configuration; nothing is switched
  and no schedule moves. A rollback switches the running version back.
  Existing projects of networks published the old way (one network per
  release) are not migrated: 0.2.2 starts from versioned networks.
- Projects (`t_bkn_project_project`): each changes one network on its own
  branch `project/<id>` of the network's lineage; projects of one network
  share its lineage. A project is visible to callers who can see its network.
- Ontology drafts (`t_bkn_project_draft`): drafting a project's ontology from the
  table structure of its data catalogs, by rules. Entity tables become object
  types with their keys checked by full-table counts; code tables become enums;
  link tables become many-to-many relations; declared foreign keys, and fields
  named for another table's key (also with a role in front, such as
  parent_lot_id), become relations checked by a full-table hit rate. A table
  without a declared key takes an identity-like field that counts unique and
  non-null. Inferred relations that cannot be counted are proposed unverified;
  ones over a field of few values (fewer than `draft.minInferredDistinct`, 10 by
  default) are proposed, not adopted. A relation proposed rather than adopted
  says why in `proposed_because`: `not_counted`, `below_suggest_hit_rate`,
  `below_adopt_hit_rate`, `few_values` or `end_not_adopted` (an object type at an
  end waits for a person). Personal fields
  (privacy keywords matched as whole words) are excluded. Names and descriptions
  from the catalog's semantic understanding come first. Items are named in the
  project's naming language: of the candidate names (the name semantic
  understanding gave, the first clause of the description and of the database
  comment) the first in that language, a name holding a Han character reading
  as Chinese; with none in it, the first. The physical name names an item only
  when it has no candidate: a name people read beats an abbreviation. The
  candidates in the other language, never the physical name, become `aliases` of object
  types, properties and relation types, leaving out those BKN refuses: one
  holding a comma, or another property's name or display name. Ids come from physical
  table and field names only, never from names semantic understanding wrote, so
  they do not change with language or with understanding run again: words
  joined by `_`, camelCase split (`customerId` gives `customer_id`). A physical
  name that is not ASCII, which BKN ids cannot hold, takes a placeholder: its
  kind's prefix and a short hash of the name (`ot_…`, `p_…`, `vt_…`, `rt_…`).
  Such ids are registered with the project and every later draft gives them
  again; ids registered earlier from semantic understanding's English short
  names are kept too. Registered ids keep their names when a new table
  would clash with them. Name matching
  compares physical names as written. Only counts and
  code-table values leave vega-backend, which is read as the caller.
- Requirement specifications (`t_bkn_project_requirement_document`,
  `t_bkn_project_requirement`): the owner uploads Markdown or plain-text
  requirement documents, split into blocks; the `bkn-project-requirements`
  bkn-agent Agent drafts the project's specification rq-n from them —
  scenarios, candidate concepts, scenario questions, business rules, conflicts
  between documents and modelling choices. Every item quotes its documents, and
  rules check it before it is kept: a quote must be found verbatim within one
  block, a rule needs one, the numbers of rules and questions must be in their
  quotes, a concept maps only to an item the draft has, a conflict needs two
  documents and gets the side the order of authority prefers (standards over
  policies over requirement documents for terms and rules, the requirement
  document for goals, scope and scenarios). What the checks drop is listed in
  `spec.rejected`. People then edit items, map concepts, resolve conflicts and
  decide choices; publishing and the regression after a release read the
  scenario questions with the drafted items they need.
- Health and readiness endpoints.

## API

Prefix: `/api/bkn-project/v1`. All routes except `/health` and `/ready` need an
OAuth token, verified through Hydra like bkn-backend's external routes. Exports
from bkn-backend run with the caller's token, so its permissions apply.

Every lineage is kept in BKN 3.0: exports ask bkn-backend for `bkn_spec=3.0`, so
`main`, the project branches and what a release reads back share the 3.0 rules,
which hold the value types a draft writes. A network bkn-backend cannot export
as 3.0 is refused with 400, `error_details` naming what to fix, and nothing is
created: `BknProject.Lineage.NetworkNeedsCheck` for action parameters its network
check flags, `BknProject.Lineage.NetworkNotReadableAsV3` for a definition that
does not read back under the 3.0 rules. A lineage
started in 2.x moves to 3.0 when its drift is committed, and its branches when
they sync.

## Knowledge-base Extension

The knowledge base of BKN projects — document sources, concept extraction, builds, acceptance, publication and refresh — is part of the professional edition (openbkn-ee). The open core keeps only the edition hooks below; in the community edition the `/kb/*` routes answer 404 and drafts hold no document items.

### Edition hooks

`server/extension/projecthooks` is the contract through which an edition adds
sources beyond tables to projects. It imports only `interfaces`, so changing it
changes the contract with the professional edition. `Register` sets three
groups once, before serving; a nil group keeps the community behaviour:

- `Drafts`: what document items add to a draft — reading, saving, Ask AI,
  confirming, exporting. The draft service reaches back through `Host`. The
  community default owns no item and refuses a draft that holds document items
  as a source out of reach.
- `Publications`: the check a release review adds and the publication a
  release prepares, mounts once written into the draft and activates once
  published. `ReleaseTarget.Version` names the release: the network keeps its
  id across releases.
- `Projects`: a step in the archive transaction, and work after it commits.

An edition registers its hooks during assembly, adds its workers with
`Application.AddWorker`, opens its stores on `Application.DB()` and installs its
routes with `Application.RegisterKnowledgeBaseRoutes`. Those routes are served
when the `knowledge_base` capability is licensed.
Handlers an edition adds share `server/driveradapters/httpx`.

## Deployment

### Database account

The chart passes the database account to the pod from a Secret as
`BKN_PROJECT_DB_USER` and `BKN_PROJECT_DB_PASSWORD`; the ConfigMap holds only the
host, port and type. By default the chart writes `depServices.rds.user` and
`depServices.rds.password` into its own Secret `bkn-project-db`; set
`depServices.rds.existingSecret` to a Secret with keys `user` and `password` to
use that instead. A change to the chart's own Secret restarts the pod; the
chart does not read an existing Secret, so after changing one restart the pod
yourself (`kubectl rollout restart deployment/bkn-project`).

Use an account other than root. The service needs only `SELECT`, `INSERT`,
`UPDATE` and `DELETE` on the `t_bkn_project_*` tables of database `openbkn`;
data-migrator creates the tables with its own account. An edition that migrates
its own tables sets `migration.enabled`: the chart then runs `migration.args`
(default `migrate`) in an init container on the service's own image, so it
follows `image.registry` and `image.tag`, with the same configuration mounted.
Give it a separate migration account through `migration.existingSecret` (a
Secret with keys `user` and `password`, passed as
`BKN_PROJECT_MIGRATION_DB_USER` / `BKN_PROJECT_MIGRATION_DB_PASSWORD`). Left
empty, the migration runs with the service account, which then needs the
migration's privileges too. `initContainers` stays for anything else an edition
runs first.

The professional edition's README lists the privileges of both accounts.

### Resources and shutdown

Requests are 100m CPU and 256Mi memory, limits 1 CPU and 1Gi. After SIGTERM the
service stops taking requests and waits up to 60 s for requests and workers to
finish; `terminationGracePeriodSeconds` is 75 so the pod is not killed first.

### Agent task input

Drafting, requirement extraction, the release judge and, in the professional
edition, concept and document extraction run as bkn-agent tasks. Each task is a
row of `t_agent_task` in database `openbkn`: `f_input` holds what was sent to the
model, which includes the text of the requirement documents and knowledge-base
files read, whether or not original text is included in the network;
`f_output` holds the model's answer.

- **What is kept:** every task row, with its input and output, until removed.
  bkn-project keeps its own results in its tables and Datasets; it reads a task
  back only while the run is going and, for a concept extraction, to recover its
  answer after an interrupted request.
- **How long:** 0.2.2 removes nothing on its own. Keep finished tasks for 30
  days, or shorter if the documents are sensitive.
- **How to clean:** remove finished tasks of the bkn-project agents older than
  the period, for example 30 days:

  ```sql
  DELETE FROM openbkn.t_agent_task
  WHERE f_agent_id LIKE 'bkn-project-%'
    AND f_status NOT IN ('pending', 'running')
    AND f_update_time < (UNIX_TIMESTAMP() - 30 * 86400) * 1000;
  ```

  Running tasks are not touched, and builds, releases and drafts do not change.
  A concept extraction interrupted before the cut can no longer be recovered
  and is run again. Traces that bkn-trace recorded for these tasks follow
  bkn-trace's own retention.

Configuration: `server/config/bkn-project-config.yaml`. The schema is created
by data-migrator from `migrations/bkn-project/`.

Drafting rules are under `draft` (defaults in brackets): `codeTableMaxRows` (500)
and `codeTableMaxColumns` (3) bound a code table; `adoptHitRate` (0.95) and
`suggestHitRate` (0.8) grade relations by hit rate; `privacyKeywords` match
personal fields by name or comment; `queryTimeout` (60 s) bounds each count and
`timeout` (10 min) the whole drafting. Drafting runs in the service process: a
restart fails drafts left drafting, as `interrupted`.

Regenerate mocks with `make generate-mock` (needs `mockgen` from
`go.uber.org/mock`).
