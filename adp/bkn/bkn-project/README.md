# BKN Project

[中文](README.zh.md) | English

`bkn-project` builds and publishes knowledge networks from projects. Each
release is imported into bkn-backend as a new knowledge network
(`<base_id>_<version>`) instead of overwriting the live one, and the release
history is kept as a lineage. See issue #2520 and epic #2519.

## Current Capability Scope

- Release lineage store (`t_bkn_project_release`).
- Git lineages: one bare repository per lineage under `/data/git` (a
  persistent volume in the Helm chart). `main` mirrors the live network;
  projects work on their own branches and sync `main` into them with a
  semantic three-way merge.
- Drift check between the live network and `main`.
- Publishing a project branch as a new network `<lineage_id>_v<major>_<minor>_<patch>`
  named `<base name> · <version>` (ids cut to 128 characters, names to 128
  characters), tagged `v<version>` in git.
- Projects (`t_bkn_project_project`): each changes one network on its own
  branch `project/<id>` of the network's lineage; projects of one network
  share its lineage. A project is visible to callers who can see its network.
- Ontology drafts (`t_bkn_project_draft`): drafting a project's ontology from the
  table structure of its data catalogs, by rules. Entity tables become object
  types with their keys checked by full-table counts; code tables become enums;
  link tables become many-to-many relations; declared foreign keys, and fields
  named for another table's key (also with a role in front, such as
  parent_lot_id), become relations checked by a full-table hit rate. A table
  without a declared key takes an identity-like field that counts unique and
  non-null. Inferred relations that cannot be counted are proposed unverified;
  ones over a field of few values (fewer than `draft.minInferredDistinct`, 10 by
  default) are proposed, not adopted. A relation proposed rather than adopted
  says why in `proposed_because`: `not_counted`, `below_suggest_hit_rate`,
  `below_adopt_hit_rate`, `few_values` or `end_not_adopted` (an object type at an
  end waits for a person). Personal fields
  (privacy keywords matched as whole words) are excluded. Names and descriptions
  from the catalog's semantic understanding come first. Items are named in the
  project's naming language: of the candidate names (the name semantic
  understanding gave, the first clause of the description and of the database
  comment) the first in that language, a name holding a Han character reading
  as Chinese; with none in it, the first. The physical name names an item only
  when it has no candidate: a name people read beats an abbreviation. The
  candidates in the other language, never the physical name, become `aliases` of object
  types, properties and relation types, leaving out those BKN refuses: one
  holding a comma, or another property's name or display name. Ids come from physical
  table and field names only, never from names semantic understanding wrote, so
  they do not change with language or with understanding run again: words
  joined by `_`, camelCase split (`customerId` gives `customer_id`). A physical
  name that is not ASCII, which BKN ids cannot hold, takes the English short name
  semantic understanding gave the table or field (`api_name`); until there is
  one, its kind's prefix and a short hash of the name stand in (`ot_…`, `p_…`,
  `vt_…`, `rt_…`). Such ids are registered with the project and every later
  draft gives them again; a placeholder gives way to a short name until a
  confirmation locks it. Registered ids keep their names when a new table
  would clash with them. Name matching
  compares physical names as written. Only counts and
  code-table values leave vega-backend, which is read as the caller.
- Requirement specifications (`t_bkn_project_requirement_document`,
  `t_bkn_project_requirement`): the owner uploads Markdown or plain-text
  requirement documents, split into blocks; the `bkn-project-requirements`
  bkn-agent Agent drafts the project's specification rq-n from them —
  scenarios, candidate concepts, scenario questions, business rules, conflicts
  between documents and modelling choices. Every item quotes its documents, and
  rules check it before it is kept: a quote must be found verbatim within one
  block, a rule needs one, the numbers of rules and questions must be in their
  quotes, a concept maps only to an item the draft has, a conflict needs two
  documents and gets the side the order of authority prefers (standards over
  policies over requirement documents for terms and rules, the requirement
  document for goals, scope and scenarios). What the checks drop is listed in
  `spec.rejected`. People then edit items, map concepts, resolve conflicts and
  decide choices; publishing and the regression after a release read the
  scenario questions with the drafted items they need.
- Health and readiness endpoints.

## API

Prefix: `/api/bkn-project/v1`. All routes except `/health` and `/ready` need an
OAuth token, verified through Hydra like bkn-backend's external routes. Exports
from bkn-backend run with the caller's token, so its permissions apply.

Every lineage is kept in BKN 3.0: exports ask bkn-backend for `bkn_spec=3.0`, so
`main`, the project branches and what a release reads back share the 3.0 rules,
which hold the value types a draft writes. A network bkn-backend cannot export
as 3.0 is refused with 400, `error_details` naming what to fix, and nothing is
created: `BknProject.Lineage.NetworkNeedsCheck` for action parameters its network
check flags, `BknProject.Lineage.NetworkNotReadableAsV3` for a definition that
does not read back under the 3.0 rules. A lineage
started in 2.x moves to 3.0 when its drift is committed, and its branches when
they sync.

## Knowledge-base Extension

`server/extension/knowledgebase` defines the K1/K2 provider seam: paginated
catalog/file/chunk reads, explicit content versions, retention holds and
sample-to-concept proposals. Community defaults return `ErrUnavailable`, never
an empty successful result. A missing locked version is `ErrVersionGone`; the
calling API must return 410 rather than substituting the latest version.
Hold creation is atomic and retryable with the same UUID and version set;
release is idempotent. Source permissions and upstream failures remain errors.

An edition entry point calls `app.Boot()`, unconditionally registers its
`knowledgebase.Providers`, optionally installs the core API adapters with
`Application.RegisterKnowledgeBaseRoutes`, and calls `Run()`. Run freezes
registration and refreshes the signed license from `BKN_SAFE_URL`. Providers
and extension routes are enabled per request from Professional upward using
the existing `knowledge_base` capability. Otherwise the complete community
router handles the request, including 404s, method handling and redirects.
Handlers still authenticate callers and authorize projects and sources.

K0 adds no business endpoints, Agent seeds, migrations or knowledge-base calls.
K1/K2 supply the adapters and real providers; Dataset writes and instance builds
are deferred to K3/K4. Proposals reuse the existing draft types and must be
validated by core before entering the human review workflow. Extensions do not
save drafts. `source_quote` remains a cross-layer column; it stays empty unless
original-text retrieval is enabled for its source catalog. Block/image rows
are likewise only written when that option is enabled.


Configuration: `server/config/bkn-project-config.yaml`. The schema is created

Drafting rules are under `draft` (defaults in brackets): `codeTableMaxRows` (500)
and `codeTableMaxColumns` (3) bound a code table; `adoptHitRate` (0.95) and
`suggestHitRate` (0.8) grade relations by hit rate; `privacyKeywords` match
personal fields by name or comment; `queryTimeout` (60 s) bounds each count and
`timeout` (10 min) the whole drafting. Drafting runs in the service process: a
restart fails drafts left drafting, as `interrupted`.

Regenerate mocks with `make generate-mock` (needs `mockgen` from
`go.uber.org/mock`).

### Interactive knowledge-base resources (K1)

The EE assembly installs four core-owned GET routes under
`/projects/{project_id}/kb`: `/knowledge-bases`, `/catalogs`, `/files`,
and `/summary`. Every request authenticates a user and checks project visibility
before accessing a source. The selected source is `knowledge_base_id`; optional
file filters are `catalog_id`, `include_subcatalogs`, repeated `mime_type`, and
`updated_since`. Lists accept `limit` (1–200) and an opaque `cursor`. Catalogs are
a flat, paginated tree carrying parent IDs. Summary uses the same file filters
and returns `file_count`, `size`, `content_version_file_count`, and `chunk_count`.

Core forwards the authenticated operator only in a redacted request context; no
credential enters a DTO, task, decision or git. Source reads require that user's
current `query_data` and never mount a network or borrow a proxy identity.
Original-version loss is 410; authentication, permission, conflict and dependency
failures remain distinct. No source response body is copied into errors.

Configure `knowledgeBase.url` in Helm (the internal API origin) to inject
`KB_API_URL`; empty leaves the source unavailable. The runtime `knowledge_base`
gate still selects the complete community router when unlicensed.

| PUT | `/selection/samples` | `selection_id`, optimistic `revision`, and `plan`; returns updated state |
| GET | `/selection/changes` | Read-only complete scan: `added`, content-version `changed`, `no_longer_in_range`; never claims global deletion or changes the selection |
| POST | `/selection/clear` | Explicit `{ "confirm_clear_all": true }`; retire current/pending sources and attempt cleanup |
| POST | `/selection/cleanup` | Retry outstanding releases using this authenticated request |

The lock first scans every selected range, deduplicating files by knowledge base
and file ID, then persists an intent before any remote retention write. A scan
error leaves no new intent. Immutable version IDs are retained in batches of at
most 1,000 per knowledge base. Timeout leaves a resumable pending operation;
unknown-UUID release tombstones prevent late creation from reviving a cancelled
hold (read contract v0.8). Replacing sources atomically activates the new manifest
before queuing the old unreferenced holds for release. Archive queues cleanup in
the same database transaction; unarchive does not revive released holds. Failed
release acknowledgements stay pending until a subsequent authenticated cleanup.
No credential is persisted and no background identity is invented.

A sample plan is `specified` with `debug_ids` and `acceptance_ids` (file keys
`knowledge_base_id/file_id`), or `random` with explicit `ratio` (0–1) and
`minimum`. Optional acceptance sampling requires both `acceptance_ratio` and
`acceptance_minimum`. There are no platform defaults pending real-directory
calibration. Random selection allocates proportionally by knowledge base/catalog,
keeps exact requested totals, and never overlaps debug and acceptance samples.
Files without a locked content version cannot be samples. Stored file metadata
provides exact file/byte/chunk totals; extraction-time estimates await measurements.

Migration `13-kb-selection.sql` adds process metadata only. `init.sql` includes the
same table for fresh installations; applied numbered upgrades are unchanged. No
models, instances or document text are stored here. The retention guard protects
published references; connecting release lineage to that guard belongs to K6.
The Studio workflow and real-service validation remain tracked in #2838.

### Bounded concept-extraction input (K2 foundation)

The optional `knowledgebase.SampleSource` reads native chunk batches from explicit KB/file/version references (read contract v0.9). Community defaults remain unavailable; this slice registers no extraction route or Agent.

`kbconcept.LoadSamples` reads only the active selection's locked `debug` files; acceptance files never enter its request. One extraction is bounded to 20 files, 500 chunks, 1,000 located fragments and 120,000 Unicode code points. Oversized input fails explicitly rather than truncating. Every native page must complete; returned file/version identities and final per-file chunk counts must match the manifest. A dependency failure, repeated cursor, duplicate chunk or unlocated selected file fails the whole input.

Disjoint native spans become independently located fragments. `ValidateCitations` requires the proposal's exact KB/file/version, block, code-point interval and quote to match one real fragment, and never joins across gaps. Its returned copy keeps a quote only for a file whose `include_original` decision permits it; otherwise the location remains with an empty quote. Live model input is transient and must not be persisted as a task, decision or draft.

The Agent, semantic model validation, candidate integration, templates and editor remain K2 follow-up work in #2839. This foundation does not change draft adoption, confirmation, Dataset creation or publication.

A selected debug file with zero chunks or no located text returns the distinct `ErrNoLocatedSamples`, so the UI can ask the owner to choose readable samples; malformed counts remain `ErrInvalidSample`. K1 sample allocation is not silently rewritten.
