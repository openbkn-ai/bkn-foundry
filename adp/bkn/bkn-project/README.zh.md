# BKN Project

中文 | [English](README.md)

`bkn-project` 基于项目构建并发布知识网络。每次发布都作为一个新的知识网络
（`<base_id>_<version>`）导入 bkn-backend，不覆盖线上网络；发布历史以谱系
（lineage）形式保存。参见 issue #2520 和 epic #2519。

## 当前能力范围

- 发布记录存储（`t_bkn_project_release`）。
- git 谱系：每个谱系一个裸仓库，位于 `/data/git`（Helm chart 中为持久卷）。
  `main` 对应网络的运行版本；各项目在自己的分支上工作，并通过语义三方合并把
  `main` 同步进分支。
- 网络草稿与 `main` 之间的漂移检查。
- 通过网络版本发布（bkn-backend 版本管理，bkn-foundry#1229）：项目的网络保留版本，
  网络 ID 不变。发布先“准备”：项目分支整包替换网络的草稿，并在草稿上回答项目的场景
  问题（`kn_version=draft`），运行版本不变；再“发布”：草稿成为运行版本，对所有使用方
  同时生效，标签为 `v<version>`，并在 git 中打标签 `v<version>`。使用方不用改配置，
  不切换、也不搬迁调度。回退就是把运行版本切回更早的版本。按旧方式（每次发布一个
  新网络）发布过的项目不做迁移：0.2.2 从版本化网络开始。
- 项目（`t_bkn_project_project`）：每个项目在所属网络谱系的分支
  `project/<id>` 上修改该网络；同一网络的项目共用一个谱系。能看到该网络的
  调用方才能看到项目。
- 本体草稿（`t_bkn_project_draft`）：按规则根据项目数据目录的表结构起草本体。
  实体表起草为对象类，主键用全表统计核对；没有声明主键的表，取一个全表唯一且无
  空值的标识类字段作为推断主键。代码表起草为枚举；关联表起草为多对多关系；声明的
  外键、以及按对方主键命名的字段（含带角色前缀的，如 parent_lot_id）起草为关系，
  用全表命中率核对。无法计数的推断关系作为"未核对"保留；取值很少的字段（少于
  `draft.minInferredDistinct`，默认 10）推断出的关系只推荐不采用。推荐而未采用的关系在
  `proposed_because` 中说明原因：`not_counted`、`below_suggest_hit_rate`、
  `below_adopt_hit_rate`、`few_values` 或 `end_not_adopted`（一端的对象类还在等人
  决定）。个人信息字段（隐私关键词按词匹配）排除。优先使用数据目录语义
  理解给出的名称和描述。名称按项目的命名语言选取：在候选名称（语义理解给出的名称、
  说明和数据库注释的第一句）中取第一个属于该语言的，含汉字的算中文；都不是该语言时取
  第一个候选。只有一个候选都没有时才用物理名：人能读懂的名称，好过缩写。另一种语言的候选写进对象类、属性和关系类的 `aliases`，物理名不进；
  BKN 不接受的别名会去掉，即含逗号的，以及与其他属性的名称或显示名相同的。ID 只由物理表名、字段名生成，不使用语义理解写回的名称，因此
  不随语言或重新理解而变化：按词用 `_` 连接，驼峰拆开（`customerId` 得到 `customer_id`）。
  物理名不是 ASCII 时（BKN 的 ID 不能含中文），使用语义理解给表或字段的英文短名
  （`api_name`）；还没有短名时，先用类别前缀加名称的短哈希占位（`ot_…`、`p_…`、`vt_…`、
  `rt_…`）。这类 ID 登记在项目里，之后每次起草都给出同一个 ID；占位在确认锁定之前可以被短名
  替换。新表与已登记的 ID 重名时，已登记的 ID 保持不变。名称匹配按物理名原文比较。以调用方身份读取 vega-backend，只取回计数
  和代码表取值。
- 需求规格（`t_bkn_project_requirement_document`、`t_bkn_project_requirement`）：
  负责人上传 Markdown 或纯文本需求资料，按段落切分；bkn-agent 的
  `bkn-project-requirements` 据此起草项目的需求规格 rq-n——业务场景、候选概念、
  场景问题、业务规则、文档之间的冲突和建模取舍。每一条都引用原文，保留前按规则核对：
  引文必须能在某一段落中逐字找到，业务规则必须有引文，规则和问题里的数字必须出现在引文中，
  概念只能对应草稿里存在的条目，冲突必须涉及两份文档，并按权威顺序给出建议方（术语和规则：
  标准优先于制度规范，再优先于需求文档；目标、范围和场景以需求文档为准）。核对没通过的条目
  列在 `spec.rejected`。之后由人编辑条目、对应概念、裁决冲突、选择取舍；发布确认和发布后
  回归读取场景问题及其依赖的草稿条目。
- 健康检查与就绪检查接口。

## API

前缀：`/api/bkn-project/v1`。除 `/health` 和 `/ready` 外的接口都需要 OAuth
令牌，与 bkn-backend 的外部接口一样通过 Hydra 校验。从 bkn-backend 导出时使用
调用方的令牌，因此 bkn-backend 的权限同样生效。

所有谱系都按 BKN 3.0 保存：导出时向 bkn-backend 请求 `bkn_spec=3.0`，`main`、
项目分支和发布读回的内容都遵循 3.0 规则，草稿写出的值类型只有 3.0 能容纳。
bkn-backend 无法按 3.0 导出的网络以 400 拒绝，`error_details` 指出要修正的内容，
不会建出任何东西：行动参数未通过网络检查时为 `BknProject.Lineage.NetworkNeedsCheck`，
有定义按 3.0 规则读不回时为 `BknProject.Lineage.NetworkNotReadableAsV3`。以 2.x
开始的谱系在提交漂移时转为 3.0，其分支在同步时转为 3.0。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | 服务信息 |
| GET | `/ready` | 数据库可达时返回 200，否则返回 503 |
| GET | `/lineages/{lineage_id}/releases?limit=&cursor=` | 谱系下的发布记录，按时间倒序，游标分页。`state` 为 `prepared`（已写入草稿，尚未发布）、`published`（带 `kn_version`，即它运行时的网络版本号），或 `legacy`（按旧方式每次发布一个新网络时的记录，版本号仍被占用） |
| GET | `/lineages/{lineage_id}/releases/{version}` | 谱系中版本号为 `version` 的发布记录 |
| POST | `/lineages/{lineage_id}/releases` | 请求体 `{"branch","version","project_id","notes","overwrite_draft_changes","allow_outdated_base"}`。把分支准备到网络草稿并立即发布，中间不跑回归：返回 201 `{"release","network_id","tag","commit","kn_version","warnings","published_metrics","purged_version"}`。409 `Release.NotVersioned`、`BranchBehind`（先同步分支）、`Drift`（草稿里有不在 `main` 中的修改；先提交漂移再同步）、`VersionExists`、`CapabilitiesSkipped`、`DraftHasChanges`（有人改了草稿还没发布：先把这些修改提交到项目，或带 `overwrite_draft_changes`）、`DraftChanged`（准备之后草稿又变了）、`DraftOutdated`（运行版本在这次发布的基础版本之后被回退过；负责人确认带回后带 `allow_outdated_base`）、`RunningChanged`、`NothingToPublish`（网络没有变化）；400 `ValidationFailed`（bkn-backend 的问题清单在 `error_details`）；503 `NotReady`。发布时带准备时的修订号 `expected_draft_revision`、`fail_on_skipped_sources`（网络的智能体读不到某个数据来源时拒绝发布，因为回归用的是发布人自己的权限，看不出这种缺口），以及由项目、版本号和请求摘要组成的 `Idempotency-Key`。请求和幂等键在发出前就存进发布记录：回复丢失后的重试原样重发，拿到第一次的结果；被 bkn-backend 拒绝的请求不再保留，下一次是带新幂等键的新请求；再次发布会补完 git 步骤。版本来源里仍记下发布记录 ID，供版本列表对应 |
| POST | `/lineages` | 请求体 `{"kn_id"}`。导出网络的运行版本并在 `main` 上创建谱系；返回 201 `{"lineage_id","commit"}`，已存在返回 409 |
| POST | `/lineages/{lineage_id}/branches` | 请求体 `{"name","from"}`（`from` 默认 `main`）；返回 201 `{"name","commit"}`，已存在返回 409 |
| PUT | `/lineages/{lineage_id}/branches/{branch}/definitions?message=` | 请求体为 bkn-backend 导出格式的 BKN tar 包（`application/octet-stream`，最大 64 MiB），替换分支上的定义；返回 `{"commit","changed":{"added","changed","removed"}}`。对 `main` 返回 403 |
| POST | `/lineages/{lineage_id}/branches/{branch}/sync` | 把 `main` 同步进分支；返回 `{"result":"up_to_date"\|"fast_forward"\|"merged","commit","summary"}`，有冲突时返回 409，冲突列表在 `error_details` 中 |
| POST | `/lineages/{lineage_id}/drift?commit=` | 请求体 `{"kn_id"}`。比较网络草稿与 `main`；返回 `{"lineage_id","kn_id","added","changed","removed","commit"}`。`commit=true` 时把草稿的定义提交到 `main` |
| POST | `/projects` | 请求体 `{"name","kn_id"\|"new_kn":{"name","id"},"catalog_ids","naming_language"}`；`naming_language` 是项目给本体项取名用的语言（`zh-CN` 或 `en-US`，否则 400 `Project.InvalidNamingLanguage`），默认为调用方的界面语言；`kn_id`（调用方可见的已有网络）和 `new_kn`（新建网络）必须且只能给一个。`new_kn` 建的网络一开始就是版本化的。还没开启版本管理的已有网络，只有带 `"enable_versioning": true`（负责人确认：此后这个网络的所有修改都要发布才生效）才会开启：不带时 409 `Project.VersioningRequired`，调用方不能修改该网络时 403 `Project.VersioningForbidden`。网络没有谱系时先创建谱系，再创建分支 `project/<id>`；返回 201 和项目。调用方为负责人 |
| GET | `/projects?archived=&name=&limit=&cursor=` | 调用方可见网络下的项目，按时间倒序，游标分页。`archived` 为 `false`（默认）、`true` 或 `all`；`name` 按包含匹配。每条带 `other_projects`：同一网络下其他未归档项目的数量 |
| GET | `/projects/{project_id}` | 项目详情；调用方看不到其网络时同样返回 404 |
| POST | `/projects/{project_id}:archive`、`:unarchive` | 归档（默认列表不显示）或取消归档，只有负责人可以操作（否则 403），不影响已发布版本。知识网络被删后，负责人仍可归档项目 |
| PUT | `/projects/{project_id}/catalogs` | 替换项目起草所用的数据目录。请求体 `{"catalog_ids"}`（必填，可为空数组，自动去重）。只有负责人可以操作（否则 403）。草稿保持不变，重新起草时读取新的目录。400 `Project.InvalidRequestBody`、`Project.InvalidCatalogIDs`；所选目录在 vega 中已不存在时 409 `Project.CatalogMissing`（details 为这些 id）；负责人无权查看详情的目录仍可设置 |
| POST | `/projects/{project_id}/catalogs:add` | 以负责人身份为项目增加数据目录，并在后台把新目录的表起草进就绪的草稿：返回 202 和草稿，草稿仍为 `ready`、可以继续编辑，`adding` 给出正在增加的目录、操作人和开始时间 `since`；它按读到的草稿写入，读取之后有人改过则返回 409 `Draft.Stale`。请求体 `{"catalog_ids"}`。只起草新目录的表；草稿中对象类所在的表也会读入，供新表与其建立关系，但不会重新计数。草稿已有的条目、决定和确认都保持原样。新的对象类、值类型以及至少一端是新对象类的关系会被加入，并带上 `added_by_catalog`，即起草出它们的目录；关系端点若是草稿已有的对象类，就沿用其 ID 和映射同一字段的属性；新 ID 与草稿已有 ID 冲突时取下一个空闲后缀。完成后新条目并入当时最新的草稿（含期间的编辑），清除 `adding`，更新时间前移，并记一条 `add_catalogs` 决定（kind 为 `draft`），列出增加的目录和条目；起草失败时草稿条目不变，决定中给出 `error`，该目录可以再次增加。新目录中起草本身读不到的表计入 `unreadable`，草稿记为部分起草。期间草稿被重新起草，或增加过程未能记录就结束（`adding` 早于起草超时，例如服务重启），都不会写入任何内容，也不会占住草稿。400 `Project.InvalidCatalogIDs`（为空、空值、重复，或草稿已从该目录起草过：`error_details.drafted`）、`Draft.InvalidRequestBody`；403 `Draft.NotOwner`；409 `Draft.NotReady`（还没有草稿时请用 `draft:generate`）、`Draft.Drafting`（正在增加目录）、`Draft.Stale`、`Draft.CatalogMissing`、`Draft.ProjectArchived`。`PUT /projects/{project_id}/catalogs` 仍是整体替换 |
| PUT | `/projects/{project_id}/naming-language` | 设置项目给本体项取名用的语言。请求体 `{"naming_language"}`：`zh-CN` 或 `en-US`。只有负责人可以操作（否则 403）。草稿保持原有名称，重新起草时按新语言取名。设置命名语言之前创建的项目按 `zh-CN` 处理。400 `Project.InvalidRequestBody`、`Project.InvalidNamingLanguage` |
| POST | `/projects/{project_id}/catalogs:understand` | 对项目所选数据目录中的表启动 vega-backend 的语义理解。它会补上表和字段的显示名、描述和英文短名，起草时会用到，建议在起草前运行。仅负责人：403 `Understand.NotOwner`。请求体可选：`apply_mode`——`fill_empty`（默认：只填写空缺的内容，保留人工编辑）或 `force`（覆盖名称和描述；英文短名不会被覆盖）；`all`——为 `true` 时所有表重新理解，否则只提交还没理解过、也不在排队或运行中的表（已完成的预览，即 `dry_run`，没有写入，会再次提交；置信度不足而没有写入的结果不会）。语言使用项目的命名语言。负责人没有任务权限（`task_manage`）的目录会被跳过。返回 202 和 `catalogs`（`catalog_id`、`permitted`、`tables`：提交的表数）；任务在后台创建并逐个执行，一个项目可能需要几分钟。400 `Understand.InvalidApplyMode`、`Draft.InvalidRequestBody`；409 `Understand.NoCatalogs`、`Draft.ProjectArchived` |
| GET | `/projects/{project_id}/catalogs/understanding` | 项目所选数据目录中各表的语义理解进度，以调用方身份从 vega-backend 读取：`catalogs` 含 `catalog_id`、`visible`（调用方看不到该目录的任务时为 false，即没有 `task_manage`，进度未知）、按状态的 `counts` 和 `tables`（`resource_id`、`name`、`status`：取自该表最近一次任务，为 `not_started`、`pending`、`running`、`completed`、`failed` 或 `cancelled`；`applied`，是否已写入结果；`finish_time`） |
| GET | `/projects/{project_id}/status` | 项目当前所处的位置，按调用者从草稿、确认记录和校验结果实时计算，不存储；同样的数据返回同样的结果（`computed_at` 和调用者能做什么除外）。`stage`：`archived`、`no_draft`、`drafting`、`draft_failed`、`deciding`、`ready_to_confirm`、`check_not_started`、`checking`、`check_needs_attention`、`confirmed` 或 `published`（谱系最新一次已发布的发布是本项目的，且晚于当前确认；此时 `release` 给出它的 `version`、`network_id` 和 `kn_version`；网络运行的是其他版本时（例如回退之后），`rolled_back` 为 true，`running` 给出运行版本的 `kn_version` 和 `label`，下一步是重新发布 `review_release`，不再提供 `review_rollback`）。`blockers`（`code`、`count`、`waiting_for`：`owner`、`editor` 或 `system`）：`no_catalogs`、`needs_identity`、`unadopted_ends`、`nothing_adopted`、`branch_not_v3`、`lineage_not_v3`、`definitions_exist`（草稿可以确认时，事先读取项目分支得到）、`check_issues`、`check_partial`、`check_failed`。`undecided` 是起草时没采纳、也还没人决定的项数（在 `pending` 中列出）；`undecided_needed` 是其中就绪需求规格的知识类问题需要的项数，不带它们确认，这些问题就答不上来。它不阻断确认。`unresolved_conflicts` 是草稿可以确认时，就绪需求规格中文档之间尚未裁决的冲突数（含已提交业务确认的），不阻断确认。`draft.placeholders` 是草稿里非 ASCII 名称中仍用占位 ID 的项数；对其数据目录运行语义理解后重新起草，就会换成英文短名。已被确认锁定的占位不再改变，不计入。它不阻断确认。`stale`：`confirmation_outdated`、`check_outdated`。`next_actions`：可以发出的请求，包括 `action`（`archive`、`unarchive`、`understand_catalogs`、`set_catalogs`、`generate_draft`、`adopt_items`、`confirm_draft`、`run_check`、`sync_branch` 和 `commit_drift`（项目自己的 `branch:sync`、`drift:commit`，仅负责人）、`review_release`（校验通过或部分未核对之后；路径带 `?version=`，即 `suggested_version`：谱系最新发布的下一个补丁号，首次发布为 1.0.0；`requires: ["version"]` 表示客户端可以改用别的版本号）、`review_rollback`（已发布后，仅负责人）、`wait`）、`method`、相对 API 根的 `path`、`body` 模板、调用者能否发出 `allowed`（不能时带 `reason`：`not_owner`、`running` 或阻断项的 code）、`wait` 的 `retry_after_s`、重新起草会丢弃的 `discards_decisions`，以及确认所带的 `accepts`：认可部分起草（`partial_draft`）、认可暂不纳入未决项（`undecided_items`），或认可需求冲突尚未裁决（`unresolved_conflicts`，请求体带 `accept_unresolved_conflicts`）。`links` 指向草稿、待定项、校验和索引就绪度。`data_sources`（起草中不返回，其余阶段都读取，包括已归档）：`network`（项目在 bkn-backend 中的知识网络）、`catalogs`（数据目录）和 `tables`（已采用对象类的表，以及已采用关系类的连接表；值类型的取值已写入定义，不算），各带 `state`（`ok`、`missing`、`unreachable` | GET | `/projects/{project_id}/rollback-plan?to_version=` | 把网络的运行版本切回更早版本会做什么，能读项目的人都可读取；不做任何改动。目标是 `to_version`，不带时为上一版；社区版（`full_history: false`）只能回到上一版。`from`、`to`（`kn_version`、`label`，以及由本谱系发布时的 `version`）；没有可回退的版本时没有 `to`。`questions`：项目的场景问题，按发布检查的方式归类，用目标版本的定义对照运行版本的定义：`unanswerable` 会缺少所需内容，列在 `missing`；`affected` 所依赖的内容会被回退改变；`answerable_new` 回退后才能回答。`refusals`：`Rollback.NoPrevious`、`Rollback.NotProjectRelease`（运行版本是其他项目发布的，只有该项目能回退）、`Rollback.EditionRestricted`、`Release.NotFound`、`Release.VersionPurged`（只保留了记录：从项目历史复制后重新发布）、`Rollback.NotActivatable`。`signature` 代表运行版本和目标。本项目的发布发布后，状态会提供 `review_rollback`。404 同 `GET /projects/{project_id}` |
| POST | `/projects/{project_id}/rollbacks` | 请求体 `{"signature","to_version"}`，取自回退预检。重新计算预检，仍然成立时把运行版本切换到目标版本，对所有使用方同时生效，并要求运行版本仍是预检时的版本：返回 200 `{"running_version","warnings"}`。不导入，草稿和项目分支保持不变；之后基于较新内容的发布会被拒绝为 `Release.DraftOutdated`，直到负责人确认带回。仅项目负责人：403 `Release.NotOwner`；409 `Release.ProjectArchived`。400 `Rollback.PrecheckRequired`（未带签名）、`Release.InvalidRequestBody`；409 `Rollback.PlanOutdated`（预检之后运行版本变了）、`Rollback.BrokenReferences`（目标版本引用的内容已经不存在），以及预检中的拒绝原因 |

## 知识库扩展

BKN 项目的知识库能力（文档来源、概念抽取、构建、验收、发布和刷新）属于专业版（openbkn-ee）。开源核心只保留下面的版本扩展钩子；社区版的 `/kb/*` 接口返回 404，草稿不含文档条目。

### 版本扩展钩子

`server/extension/projecthooks` 是版本给项目增加表以外数据来源的契约，只依赖
`interfaces`，改它就是改与专业版的契约。`Register` 在开始服务前一次设置三组钩子，
未设置的组保持社区版行为：

- `Drafts`：文档条目对草稿的读取、保存、问 AI、确认和导出；草稿服务经 `Host`
  回调。社区默认不认领任何条目，草稿含文档条目时按来源不可达拒绝。
- `Publications`：发布审查增加的检查；发布时的准备、写入草稿后挂载、发布后激活。
  `ReleaseTarget.Version` 标明是哪次发布：网络在各次发布之间保持同一个 ID。
- `Projects`：归档事务内的一步，以及提交后的后续处理。

版本在装配时注册钩子，用 `Application.AddWorker` 加后台任务，用 `Application.DB()` 打开存储，
用 `Application.RegisterKnowledgeBaseRoutes` 安装路由；路由在 `knowledge_base` 能力已授权时生效。
版本增加的处理器共用 `server/driveradapters/httpx`。

## 部署

### 数据库账号

chart 通过 Secret 把数据库账号以 `BKN_PROJECT_DB_USER`、`BKN_PROJECT_DB_PASSWORD`
传给容器，ConfigMap 只保留地址、端口和类型。默认 chart 把 `depServices.rds.user`、
`depServices.rds.password` 写入自己的 Secret `bkn-project-db`；设置
`depServices.rds.existingSecret` 为一个含 `user`、`password` 两个键的 Secret 时改用它。
chart 自己的 Secret 变化会重启 Pod；chart 不读取已有的 Secret，改了它之后需要手动重启
（`kubectl rollout restart deployment/bkn-project`）。

不要使用 root。服务只需要 `openbkn` 库里 `t_bkn_project_*` 表的 `SELECT`、`INSERT`、
`UPDATE`、`DELETE`；表由 data-migrator 用它自己的账号创建。版本需要迁移
自己的表时设置 `migration.enabled`：chart 在 init 容器里用服务自己的镜像运行 `migration.args`
（默认 `migrate`），镜像随 `image.registry`、`image.tag` 一起变，并挂同一份配置。用
`migration.existingSecret`（含 `user`、`password` 两个键的 Secret，以
`BKN_PROJECT_MIGRATION_DB_USER`、`BKN_PROJECT_MIGRATION_DB_PASSWORD` 传入）给它单独的迁移账号；
留空时用服务账号迁移，这时服务账号也要有迁移权限。`initContainers` 仍可放版本要先运行的其他容器。

两个账号的权限见专业版 README。

### 资源和停止

请求 100m CPU、256Mi 内存，上限 1 CPU、1Gi。收到 SIGTERM 后服务不再接收请求，
最多等 60 秒让请求和后台任务结束；`terminationGracePeriodSeconds` 为 75，Pod 不会先被强制结束。

### Agent 任务输入

起草、需求抽取、发布评审，以及专业版的概念抽取和文档抽取都作为 bkn-agent 任务运行。
每个任务是 `openbkn` 库 `t_agent_task` 里的一行：`f_input` 是发给模型的内容，包括读取的
需求文档和知识库文件正文，与网络是否纳入原文无关；`f_output` 是模型的回答。

- **保留什么：** 每个任务的行及其输入和输出，直到被删除。bkn-project 的结果保存在
  自己的表和 Dataset 里；它只在运行过程中回读任务，概念抽取请求中断后用它找回回答。
- **保留多久：** 0.2.2 不会自动删除。建议已结束的任务保留 30 天；文档敏感时可以更短。
- **怎么清理：** 删除超过保留期、已结束的 bkn-project Agent 任务，例如 30 天：

  ```sql
  DELETE FROM openbkn.t_agent_task
  WHERE f_agent_id LIKE 'bkn-project-%'
    AND f_status NOT IN ('pending', 'running')
    AND f_update_time < (UNIX_TIMESTAMP() - 30 * 86400) * 1000;
  ```

  运行中的任务不受影响，构建、发布和草稿不变。截止时间前中断的概念抽取不能再找回，
  需要重新运行。bkn-trace 为这些任务记录的追踪数据按 bkn-trace 自己的保留设置处理。

## 本地开发

```bash
cd server
go build ./...
go vet ./...
I18N_MODE_UT=true go test ./...
```

配置文件：`server/config/bkn-project-config.yaml`。表结构由 data-migrator
根据 `migrations/bkn-project/` 创建。

起草规则在 `draft` 下（括号内为默认值）：`codeTableMaxRows`（500）和
`codeTableMaxColumns`（3）界定代码表；`adoptHitRate`（0.95）和 `suggestHitRate`
（0.8）按命中率给关系分档；`privacyKeywords` 按字段名或注释匹配个人信息；
`queryTimeout`（60 秒）限制每条计数查询，`timeout`（10 分钟）限制整次起草。起草在
服务进程内运行：重启时仍在起草中的草稿置为失败，原因为 `interrupted`。

使用 `make generate-mock` 重新生成 mock（需要 `go.uber.org/mock` 的 `mockgen`）。
