# BKN Project

中文 | [English](README.md)

`bkn-project` 基于项目构建并发布知识网络。每次发布都作为一个新的知识网络
（`<base_id>_<version>`）导入 bkn-backend，不覆盖线上网络；发布历史以谱系
（lineage）形式保存。参见 issue #2520 和 epic #2519。

## 当前能力范围

- 发布谱系存储（`t_bkn_project_release`）。
- git 谱系：每个谱系一个裸仓库，位于 `/data/git`（Helm chart 中为持久卷）。
  `main` 对应线上网络；各项目在自己的分支上工作，并通过语义三方合并把
  `main` 同步进分支。
- 线上网络与 `main` 之间的漂移检查。
- 把项目分支发布为新网络 `<lineage_id>_v<major>_<minor>_<patch>`，名称为
  `<基础名称> · <版本>`（ID 与名称均截断到 128 个字符），并在 git 中打标签 `v<version>`。
- 项目（`t_bkn_project_project`）：每个项目在所属网络谱系的分支
  `project/<id>` 上修改该网络；同一网络的项目共用一个谱系。能看到该网络的
  调用方才能看到项目。
- 本体草稿（`t_bkn_project_draft`）：按规则根据项目数据目录的表结构起草本体。
  实体表起草为对象类，主键用全表统计核对；没有声明主键的表，取一个全表唯一且无
  空值的标识类字段作为推断主键。代码表起草为枚举；关联表起草为多对多关系；声明的
  外键、以及按对方主键命名的字段（含带角色前缀的，如 parent_lot_id）起草为关系，
  用全表命中率核对。无法计数的推断关系作为"未核对"保留；取值很少的字段（少于
  `draft.minInferredDistinct`，默认 10）推断出的关系只推荐不采用。推荐而未采用的关系在
  `proposed_because` 中说明原因：`not_counted`、`below_suggest_hit_rate`、
  `below_adopt_hit_rate`、`few_values` 或 `end_not_adopted`（一端的对象类还在等人
  决定）。个人信息字段（隐私关键词按词匹配）排除。优先使用数据目录语义
  理解给出的名称和描述。名称按项目的命名语言选取：在候选名称（语义理解给出的名称、
  说明和数据库注释的第一句）中取第一个属于该语言的，含汉字的算中文；都不是该语言时取
  第一个候选。只有一个候选都没有时才用物理名：人能读懂的名称，好过缩写。另一种语言的候选写进对象类、属性和关系类的 `aliases`，物理名不进；
  BKN 不接受的别名会去掉，即含逗号的，以及与其他属性的名称或显示名相同的。ID 只由物理表名、字段名生成，不使用语义理解写回的名称，因此
  不随语言或重新理解而变化：按词用 `_` 连接，驼峰拆开（`customerId` 得到 `customer_id`）。
  物理名不是 ASCII 时（BKN 的 ID 不能含中文），使用语义理解给表或字段的英文短名
  （`api_name`）；还没有短名时，先用类别前缀加名称的短哈希占位（`ot_…`、`p_…`、`vt_…`、
  `rt_…`）。这类 ID 登记在项目里，之后每次起草都给出同一个 ID；占位在确认锁定之前可以被短名
  替换。新表与已登记的 ID 重名时，已登记的 ID 保持不变。名称匹配按物理名原文比较。以调用方身份读取 vega-backend，只取回计数
  和代码表取值。
- 需求规格（`t_bkn_project_requirement_document`、`t_bkn_project_requirement`）：
  负责人上传 Markdown 或纯文本需求资料，按段落切分；bkn-agent 的
  `bkn-project-requirements` 据此起草项目的需求规格 rq-n——业务场景、候选概念、
  场景问题、业务规则、文档之间的冲突和建模取舍。每一条都引用原文，保留前按规则核对：
  引文必须能在某一段落中逐字找到，业务规则必须有引文，规则和问题里的数字必须出现在引文中，
  概念只能对应草稿里存在的条目，冲突必须涉及两份文档，并按权威顺序给出建议方（术语和规则：
  标准优先于制度规范，再优先于需求文档；目标、范围和场景以需求文档为准）。核对没通过的条目
  列在 `spec.rejected`。之后由人编辑条目、对应概念、裁决冲突、选择取舍；发布确认和发布后
  回归读取场景问题及其依赖的草稿条目。
- 健康检查与就绪检查接口。

## API

前缀：`/api/bkn-project/v1`。除 `/health` 和 `/ready` 外的接口都需要 OAuth
令牌，与 bkn-backend 的外部接口一样通过 Hydra 校验。从 bkn-backend 导出时使用
调用方的令牌，因此 bkn-backend 的权限同样生效。

所有谱系都按 BKN 3.0 保存：导出时向 bkn-backend 请求 `bkn_spec=3.0`，`main`、
项目分支和发布读回的内容都遵循 3.0 规则，草稿写出的值类型只有 3.0 能容纳。
bkn-backend 无法按 3.0 导出的网络以 400 拒绝，`error_details` 指出要修正的内容，
不会建出任何东西：行动参数未通过网络检查时为 `BknProject.Lineage.NetworkNeedsCheck`，
有定义按 3.0 规则读不回时为 `BknProject.Lineage.NetworkNotReadableAsV3`。以 2.x
开始的谱系在提交漂移时转为 3.0，其分支在同步时转为 3.0。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | 服务信息 |
| GET | `/ready` | 数据库可达时返回 200，否则返回 503 |
| GET | `/lineages/{lineage_id}/releases?limit=&cursor=` | 谱系下的发布记录，按时间倒序，游标分页。最新一次发布的 `state` 为 `live`，更早的为 `archived`；切换使用方不改变状态 |
| GET | `/releases/{network_id}` | 产生该网络的发布记录 |
| POST | `/lineages/{lineage_id}/releases` | 请求体 `{"branch","version","project_id","notes"}`。发布该分支：返回 201 `{"release","network_id","tag","commit"}`。409 `BranchBehind`（请先同步分支）、`Drift`（路径见 `error_details`，请提交漂移并同步）、`VersionExists`、`UnfinishedAttempt`（这个版本号此前的一次发布打了标签后中断、可能已导入网络但未记录发布，而标签在另一个分支头上；`error_details` 给出 `tag`、标签的 `commit`、当前 `branch_commit` 和 `network_id`；请换新版本号发布），或 `CapabilitiesSkipped`（网络已导入但未记录发布）。任何这类失败（包括发布记录写入失败）之后，从同一分支头以同一版本重新发布，会覆盖那次导入的网络并补写发布记录 |
| POST | `/lineages` | 请求体 `{"kn_id"}`。导出线上网络并在 `main` 上创建谱系；返回 201 `{"lineage_id","commit"}`，已存在返回 409 |
| POST | `/lineages/{lineage_id}/branches` | 请求体 `{"name","from"}`（`from` 默认 `main`）；返回 201 `{"name","commit"}`，已存在返回 409 |
| PUT | `/lineages/{lineage_id}/branches/{branch}/definitions?message=` | 请求体为 bkn-backend 导出格式的 BKN tar 包（`application/octet-stream`，最大 64 MiB），替换分支上的定义；返回 `{"commit","changed":{"added","changed","removed"}}`。对 `main` 返回 403 |
| POST | `/lineages/{lineage_id}/branches/{branch}/sync` | 把 `main` 同步进分支；返回 `{"result":"up_to_date"\|"fast_forward"\|"merged","commit","summary"}`，有冲突时返回 409，冲突列表在 `error_details` 中 |
| POST | `/lineages/{lineage_id}/drift?commit=` | 请求体 `{"kn_id"}`。比较线上网络与 `main`；返回 `{"lineage_id","kn_id","added","changed","removed","commit"}`。`commit=true` 时把线上定义提交到 `main` |
| GET | `/lineages/{lineage_id}/switch-plan?to=` | 把谱系的使用方切换到网络 `to` 会做什么：返回 `{"lineage_id","from_network_id","to_network_id","schedules"}`，即当前所用网络上正在运行的调度。智能体、MCP、workshop、eval 及 `to` 上的权限由各自负责人切换。400 `InvalidSwitchTarget`（不是该谱系的网络），409 `AlreadyInUse` |
| POST | `/lineages/{lineage_id}/switches` | 请求体 `{"to_network_id","from_network_id"}`；可选的 `from_network_id` 是调用方预期的在用网络，若此后使用方已被其他切换移走，会在谱系锁内以 409 `Lineage.InUseChanged` 拒绝。在目标网络上启用每个运行中的调度（以切换人身份执行），在当前网络上停用，然后记录这次切换：返回 201 和切换记录。回退就是切回之前的网络，上次停用的对应调度会重新启用 |
| POST | `/projects` | 请求体 `{"name","kn_id"\|"new_kn":{"name","id"},"catalog_ids","naming_language"}`；`naming_language` 是项目给本体项取名用的语言（`zh-CN` 或 `en-US`，否则 400 `Project.InvalidNamingLanguage`），默认为调用方的界面语言；`kn_id`（调用方可见的已有网络）和 `new_kn`（新建网络）必须且只能给一个。传入某次发布产生的网络时，项目并入其原网络的谱系。网络没有谱系时先创建谱系，再创建分支 `project/<id>`；返回 201 和项目。调用方为负责人 |
| GET | `/projects?archived=&name=&limit=&cursor=` | 调用方可见网络下的项目，按时间倒序，游标分页。`archived` 为 `false`（默认）、`true` 或 `all`；`name` 按包含匹配。每条带 `other_projects`：同一网络下其他未归档项目的数量 |
| GET | `/projects/{project_id}` | 项目详情；调用方看不到其网络时同样返回 404 |
| POST | `/projects/{project_id}:archive`、`:unarchive` | 归档（默认列表不显示）或取消归档，只有负责人可以操作（否则 403），不影响已发布版本。知识网络被删后，负责人仍可归档项目 |
| PUT | `/projects/{project_id}/catalogs` | 替换项目起草所用的数据目录。请求体 `{"catalog_ids"}`（必填，可为空数组，自动去重）。只有负责人可以操作（否则 403）。草稿保持不变，重新起草时读取新的目录。400 `Project.InvalidRequestBody`、`Project.InvalidCatalogIDs`；所选目录在 vega 中已不存在时 409 `Project.CatalogMissing`（details 为这些 id）；负责人无权查看详情的目录仍可设置 |
| POST | `/projects/{project_id}/catalogs:add` | 以负责人身份为项目增加数据目录，并在后台把新目录的表起草进就绪的草稿：返回 202 和草稿，草稿仍为 `ready`、可以继续编辑，`adding` 给出正在增加的目录、操作人和开始时间 `since`；它按读到的草稿写入，读取之后有人改过则返回 409 `Draft.Stale`。请求体 `{"catalog_ids"}`。只起草新目录的表；草稿中对象类所在的表也会读入，供新表与其建立关系，但不会重新计数。草稿已有的条目、决定和确认都保持原样。新的对象类、值类型以及至少一端是新对象类的关系会被加入，并带上 `added_by_catalog`，即起草出它们的目录；关系端点若是草稿已有的对象类，就沿用其 ID 和映射同一字段的属性；新 ID 与草稿已有 ID 冲突时取下一个空闲后缀。完成后新条目并入当时最新的草稿（含期间的编辑），清除 `adding`，更新时间前移，并记一条 `add_catalogs` 决定（kind 为 `draft`），列出增加的目录和条目；起草失败时草稿条目不变，决定中给出 `error`，该目录可以再次增加。新目录中起草本身读不到的表计入 `unreadable`，草稿记为部分起草。期间草稿被重新起草，或增加过程未能记录就结束（`adding` 早于起草超时，例如服务重启），都不会写入任何内容，也不会占住草稿。400 `Project.InvalidCatalogIDs`（为空、空值、重复，或草稿已从该目录起草过：`error_details.drafted`）、`Draft.InvalidRequestBody`；403 `Draft.NotOwner`；409 `Draft.NotReady`（还没有草稿时请用 `draft:generate`）、`Draft.Drafting`（正在增加目录）、`Draft.Stale`、`Draft.CatalogMissing`、`Draft.ProjectArchived`。`PUT /projects/{project_id}/catalogs` 仍是整体替换 |
| PUT | `/projects/{project_id}/naming-language` | 设置项目给本体项取名用的语言。请求体 `{"naming_language"}`：`zh-CN` 或 `en-US`。只有负责人可以操作（否则 403）。草稿保持原有名称，重新起草时按新语言取名。设置命名语言之前创建的项目按 `zh-CN` 处理。400 `Project.InvalidRequestBody`、`Project.InvalidNamingLanguage` |
| POST | `/projects/{project_id}/catalogs:understand` | 对项目所选数据目录中的表启动 vega-backend 的语义理解。它会补上表和字段的显示名、描述和英文短名，起草时会用到，建议在起草前运行。仅负责人：403 `Understand.NotOwner`。请求体可选：`apply_mode`——`fill_empty`（默认：只填写空缺的内容，保留人工编辑）或 `force`（覆盖名称和描述；英文短名不会被覆盖）；`all`——为 `true` 时所有表重新理解，否则只提交还没理解过、也不在排队或运行中的表（已完成的预览，即 `dry_run`，没有写入，会再次提交；置信度不足而没有写入的结果不会）。语言使用项目的命名语言。负责人没有任务权限（`task_manage`）的目录会被跳过。返回 202 和 `catalogs`（`catalog_id`、`permitted`、`tables`：提交的表数）；任务在后台创建并逐个执行，一个项目可能需要几分钟。400 `Understand.InvalidApplyMode`、`Draft.InvalidRequestBody`；409 `Understand.NoCatalogs`、`Draft.ProjectArchived` |
| GET | `/projects/{project_id}/catalogs/understanding` | 项目所选数据目录中各表的语义理解进度，以调用方身份从 vega-backend 读取：`catalogs` 含 `catalog_id`、`visible`（调用方看不到该目录的任务时为 false，即没有 `task_manage`，进度未知）、按状态的 `counts` 和 `tables`（`resource_id`、`name`、`status`：取自该表最近一次任务，为 `not_started`、`pending`、`running`、`completed`、`failed` 或 `cancelled`；`applied`，是否已写入结果；`finish_time`） |
| GET | `/projects/{project_id}/status` | 项目当前所处的位置，按调用者从草稿、确认记录和校验结果实时计算，不存储；同样的数据返回同样的结果（`computed_at` 和调用者能做什么除外）。`stage`：`archived`、`no_draft`、`drafting`、`draft_failed`、`deciding`、`ready_to_confirm`、`check_not_started`、`checking`、`check_needs_attention`、`confirmed` 或 `published`（谱系最新一次发布是本项目的，且晚于当前确认；此时 `release` 给出它的 `version`、`network_id` 和 `in_use`，即谱系最近一次切换是否切到了它）。`blockers`（`code`、`count`、`waiting_for`：`owner`、`editor` 或 `system`）：`no_catalogs`、`needs_identity`、`unadopted_ends`、`nothing_adopted`、`branch_not_v3`、`lineage_not_v3`、`definitions_exist`（草稿可以确认时，事先读取项目分支得到）、`check_issues`、`check_partial`、`check_failed`。`undecided` 是起草时没采纳、也还没人决定的项数（在 `pending` 中列出）；`undecided_needed` 是其中就绪需求规格的知识类问题需要的项数，不带它们确认，这些问题就答不上来。它不阻断确认。`unresolved_conflicts` 是草稿可以确认时，就绪需求规格中文档之间尚未裁决的冲突数（含已提交业务确认的），不阻断确认。`draft.placeholders` 是草稿里非 ASCII 名称中仍用占位 ID 的项数；对其数据目录运行语义理解后重新起草，就会换成英文短名。已被确认锁定的占位不再改变，不计入。它不阻断确认。`stale`：`confirmation_outdated`、`check_outdated`。`next_actions`：可以发出的请求，包括 `action`（`archive`、`unarchive`、`understand_catalogs`、`set_catalogs`、`generate_draft`、`adopt_items`、`confirm_draft`、`run_check`、`sync_branch` 和 `commit_drift`（项目自己的 `branch:sync`、`drift:commit`，仅负责人）、`review_release`（校验通过或部分未核对之后；路径带 `?version=`，即 `suggested_version`：谱系最新发布的下一个补丁号，首次发布为 1.0.0；`requires: ["version"]` 表示客户端可以改用别的版本号）、`switch_consumers`（已发布、使用方还没切过去时，仅负责人）、`wait`）、`method`、相对 API 根的 `path`、`body` 模板、调用者能否发出 `allowed`（不能时带 `reason`：`not_owner`、`running` 或阻断项的 code）、`wait` 的 `retry_after_s`、重新起草会丢弃的 `discards_decisions`，以及确认所带的 `accepts`：认可部分起草（`partial_draft`）、认可暂不纳入未决项（`undecided_items`），或认可需求冲突尚未裁决（`unresolved_conflicts`，请求体带 `accept_unresolved_conflicts`）。`links` 指向草稿、待定项、校验和索引就绪度。`data_sources`（起草中不返回，其余阶段都读取，包括已归档）：`network`（项目在 bkn-backend 中的知识网络）、`catalogs`（数据目录）和 `tables`（已采用对象类的表，以及已采用关系类的连接表；值类型的取值已写入定义，不算），各带 `state`（`ok`、`missing`、`unreachable` 表示服务没有给出答复、`not_bound` 表示还没有可依赖的对象）、`total` 和 `missing`；`tables.affected` 列出数据表已不存在的条目（`kind` 为 `object_types` 或 `relation_types`，以及 `id`、`name`、`table`）。不存在指 bkn-backend 或 vega 回 404，或在 `ignore_missing=true` 时省略；拒绝（403）不算不存在，删除后重建的目录或表按旧 id 算作不存在。不存在的依赖排在其他阻塞项之前，等待负责人处理：`network_missing` 拒绝 `archive` 以外的所有操作（知识网络被删的项目只对负责人可读、可归档，其他人仍得到 404）；`catalog_missing` 拒绝 `generate_draft`，下一步为 `set_catalogs`；`table_missing` 拒绝 `confirm_draft`、`run_check` 和 `review_release`，下一步为重新起草；已归档的项目只显示，不改操作。`unreachable` 不阻塞。`hints`（`code`、`count`、`total`，从不阻塞）：项目所选目录中超过一半的表没有描述时为 ## 知识库扩展

`server/extension/knowledgebase` 定义 K1/K2 的提供者接口：目录、文件、切片的分页读取，
明确的内容版本、保留登记，以及样本文件到概念提议。社区版空实现返回 `ErrUnavailable`，
不会假装成功并返回空列表。锁定的版本失效时返回 `ErrVersionGone`，调用方接口须返回
410，不能改读最新版本。保留登记原子创建，以相同 UUID 和版本集合重试；释放幂等。
来源权限错误和上游故障须保留为错误。

专业版入口依次调用 `app.Boot()`、无条件注册 `knowledgebase.Providers`，按需通过
`Application.RegisterKnowledgeBaseRoutes` 安装核心 API 适配器，然后调用 `Run()`。
Run 冻结注册，并从 `BKN_SAFE_URL` 持续刷新签名授权。每次请求按现有 `knowledge_base`
能力判断，Professional 及以上才能使用提供者和扩展路由；否则交给完整社区版路由处理，
包括 404、方法判定与路径重定向。业务处理器仍须鉴权，并检查项目与来源权限。

K0 不增加业务接口、Agent 种子、迁移或真实知识库调用。K1/K2 接入适配器和真实提供者；
Dataset 写入与实例构建留到 K3/K4。概念提议复用现有草稿类型，由核心校验后进入人工
确认流程，扩展不保存草稿。`source_quote` 跨层列始终存在，目录未开启原文检索时留空；
原文块、图片行也只在开关开启时写入。

## 本地开发

```bash
cd server
go build ./...
go vet ./...
I18N_MODE_UT=true go test ./...
```

配置文件：`server/config/bkn-project-config.yaml`。表结构由 data-migrator
根据 `migrations/bkn-project/` 创建。

起草规则在 `draft` 下（括号内为默认值）：`codeTableMaxRows`（500）和
`codeTableMaxColumns`（3）界定代码表；`adoptHitRate`（0.95）和 `suggestHitRate`
（0.8）按命中率给关系分档；`privacyKeywords` 按字段名或注释匹配个人信息；
`queryTimeout`（60 秒）限制每条计数查询，`timeout`（10 分钟）限制整次起草。起草在
服务进程内运行：重启时仍在起草中的草稿置为失败，原因为 `interrupted`。

使用 `make generate-mock` 重新生成 mock（需要 `go.uber.org/mock` 的 `mockgen`）。
