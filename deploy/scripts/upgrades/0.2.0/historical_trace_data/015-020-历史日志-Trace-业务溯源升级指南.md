# 015 → 020 历史日志、Trace 和业务溯源升级指南

本工具用于把客户升级到 020 后，015 中已经存在的历史数据转换成 020 可以直接读取的数据。

工具只做离线数据转换，不修改 020 的在线查询、页面和业务逻辑，也不会把缺失的数据编造出来。

## 一、升级前准备

升级在 OpenBKN 提供的管理节点或升级工具运行环境中执行，不是在业务容器里手工安装依赖。由客户技术工程师确认：

1. 020 已部署，MariaDB、Kafka、OpenSearch 和相关服务运行正常。
2. 已暂停业务写入，避免转换期间源数据继续变化。
3. 按客户 OpenBKN 部署时使用的备份机制完成三类备份：MariaDB 备份、OpenSearch 快照、相关持久化卷/对象存储备份；记录备份编号，并确认可以按现有恢复流程恢复。备份由部署运维机制完成，不由本工具代替。
4. 在 OpenBKN 管理节点或升级运行环境中执行工具。该环境需要能访问目标集群并提供 Python 3.10+；工具启动时会检查集群和运行环境，不需要在业务容器内另配集群或安装 Python。
5. 已确认 015→020 的实际切换时间。这个时间必须是客户环境的实际时间，不能照抄示例。
6. 客户 OpenSearch 使用 HTTPS 时，准备好客户 CA 文件。

源数据、备份、转换计划和报告可能包含客户业务内容，只能保存在客户受控环境，不能提交 Git 或上传到公共位置。

## 二、执行升级

在 OpenBKN 管理节点的升级工具目录执行。部署方若已提供带依赖的升级运行环境，直接使用其中的 Python：

```bash
export BKN_HISTORY_BEFORE='<客户实际切换时间，例如 2026-10-01T00:00:00+08:00>'

# 如果在线 Core 表已经不是升级前的原始状态，再指定原始 SQL 备份。
# 不需要时不要设置这个变量。
export BKN_HISTORY_CORE_BACKUP='/客户备份目录/原始应用库.sql.gz'

# 客户 OpenSearch 使用自签 CA 时设置；公有 CA 或系统已信任时可不设置。
export BKN_HISTORY_OPENSEARCH_CA_FILE='/客户证书目录/customer-ca.pem'

python3 deploy/scripts/upgrades/0.2.0/historical_trace_data/run_upgrade.py
```

只有在管理节点没有带依赖的升级运行环境时，才创建临时虚拟环境：

```bash
python3 -m venv /tmp/openbkn-history-upgrade
/tmp/openbkn-history-upgrade/bin/pip install \
  -r deploy/scripts/upgrades/0.2.0/historical_trace_data/requirements.txt

/tmp/openbkn-history-upgrade/bin/python \
  deploy/scripts/upgrades/0.2.0/historical_trace_data/run_upgrade.py
```

工具会自动发现目标集群、冻结源数据、执行预检、转换、写入、逐项回读并生成报告。不要手工逐个导表、拼接关系或直接重放在线完成流程。工具不会创建或删除客户备份，也不会替客户恢复数据库；发生故障时按客户 OpenBKN 原有恢复流程操作。

## 三、怎么看结果

命令退出码：

- `0`：选定范围内的源记录已完成转换并通过目标端回读验证。
- `2`：仍有未完成、冲突或回读失败，需要根据报告处理，不能当作成功。

报告默认保存在：

```text
~/.bkn/upgrades/015-to-020-historical/
```

重点检查报告中的：

- 源记录数量和目标记录数量；
- 新增、已存在并跳过、默认字段、字段丢失、冲突和失败数量；
- Audit 是否在 MariaDB 原生审计表读回；
- Evidence、日志和业务溯源投影是否在 OpenSearch 读回；
- Core 的 Conversation、Interaction、Operation、Receipt、Request、Trace、Span 关系是否保留；
- 是否有整条源记录未转换。
- `retained-artifact-field-defaults.json` 中是否记录了因 020 原生内容合同拒收而做的逐条有损转换，以及对应的交互和源内容哈希。

缺少的问题正文、答案正文或技术 Span 正文时，报告会标明缺失原因；工具保留原 ID 和引用，不填入虚假内容。

## 四、重复执行和失败处理

同一客户环境可以重复执行。相同内容会被识别为已存在并跳过，不会重复创建；内容不同的目标记录会报告冲突，不会覆盖。

失败后先查看报告和备份，再直接重新运行。不要修改源表，不要手工删除目标数据，不要按时间范围、问题文本、Trace 前缀或 Agent 名称批量删除。

如果目标环境已经运行过旧的错误转换器，必须先保留目标备份和旧转换 manifest，再由负责人依据精确 ID 清理错误目标，不能使用本工具做全库清理。

## 五、OpenSearch 证书注意事项

客户的远程 OpenSearch 地址默认必须校验证书：

```bash
export BKN_HISTORY_OPENSEARCH_CA_FILE='/客户证书目录/customer-ca.pem'
```

禁止对客户远程地址关闭证书校验。`BKN_HISTORY_OPENSEARCH_TLS_VERIFY=false` 只允许用于 `localhost`、`127.0.0.1`、`::1` 或工具自动创建的本地 port-forward；远程主机或远程 IP 使用该设置会被工具拒绝。

## 六、升级后验收

使用 020 自己的页面和接口检查，不使用 015 表直接查询代替验收：

1. 日志检索：检查历史日志时间、操作、对象、操作者和结果。
2. 审计工作台：确认管理审计是日志事实的过滤视图。
3. Trace：检查 Request、Trace、Operation、Span（源中存在时）及状态、耗时和父子关系。
4. 业务溯源：检查会话、轮次、问题、结果、调用关系和业务对象关联。
5. 抽查多轮会话、多 Trace、失败调用和缺少正文的记录。
工具本身按源身份和内容幂等处理。只有在上次执行失败后恢复，或客户明确需要验证幂等性时，才重新运行并检查没有重复新增或新的冲突；正常成功的升级不要求为了验收额外重跑一次。

历史源中不存在的正文或技术 Span 不应在验收中被补造。历史图读取开关不由本工具自动修改；页面读取限制要单独记录，不能通过增加 020 兼容逻辑掩盖转换缺口。

## 七、工具组成

入口是 `run_upgrade.py`。Python 负责环境发现、源数据快照、转换编排、回读和报告；Foundry/EE 的 Go 原生命令负责 020 Core、Ledger、Artifact 和业务溯源投影的原生格式校验与导入。工程师只需要按本指南执行统一入口。
